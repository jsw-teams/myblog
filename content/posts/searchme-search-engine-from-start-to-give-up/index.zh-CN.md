这篇文章本来可以叫《如何优雅地自建一个搜索引擎》，但写到最后发现，最优雅的地方大概是：知道什么时候停手。

`searchme` 的目标并不夸张：做一个面向日常研究、新闻素材、文献检索和视频脚本准备的搜索入口。它不想复刻 Google，也不想假装一台小服务器可以吞下整个互联网。它只是希望在 `search.js.gripe` 上提供一个能用、可控、结果不要太离谱的搜索体验。

然而搜索这个东西，越看越像一句老话：你以为是在做输入框，实际上是在做世界观。

<!--more-->

## 起点：先从 SearXNG 开始

最初的方案很直接：既然 [SearXNG](https://github.com/searxng/searxng) 已经是成熟的自托管元搜索项目，那就先拿它做底座。它能聚合多个上游搜索引擎，部署成本相对可控，也比较适合作为自建搜索入口。

于是 `searchme` 的第一阶段是围绕 SearXNG 做包装：前端、API、模式切换、缓存、结果清洗、去重，以及一些更贴近自己使用场景的排序策略。

公开仓库 [jsw-teams/searchme](https://github.com/jsw-teams/searchme) 里目前也把 SearXNG 定位成“粗召回”组件：它负责把候选结果先拿回来，但不负责最终质量判断。换句话说，SearXNG 很适合当一张网，但网到什么鱼，还得自己再分拣。

问题也正是从这里开始的。

## 现实：搜索结果不是脏，是非常有生命力

一开始我们以为搜索质量不好，是因为排序还不够聪明。后来发现，排序只是最后一层体面，前面的候选集已经很热闹了。

实际爬取和聚合结果里会混进很多奇妙内容：

- 标题看起来相关，正文几乎无关；
- 搜索词只在导航栏、页脚或推荐区出现；
- 同一篇内容被转载、搬运、聚合成好几个版本；
- 短链接、跳转页、登录页、门户页挤在正常结果中间；
- 有些页面甚至已经是 404，但仍然能被抓到或被缓存中的旧线索带出来。

这时才会意识到，“能搜到”并不等于“搜得对”。搜索引擎真正难的不是返回十条链接，而是在十条链接里少放几条看起来像答案、点进去却让人怀疑人生的东西。

## 第一轮补救：权重排序、内存写入和 local_index

既然 SearXNG 拿回来的结果不够稳，那就给 `searchme` 加一层自己的判断。

这一阶段做了几类改进：

1. 权重排序：按语言、域名、来源可信度、页面类型、短链接风险、官方站点意图等因素重新打分。
2. 内存写入：把已经见过、判断过、效果不错或效果很差的结果留在本地记忆里。
3. `local_index`：对抓取过的页面内容做本地缓存和召回实验，让后续搜索不只依赖上游搜索返回的标题和摘要。
4. 去重和过滤：规范化 URL，合并重复页面，降低低价值站点、搬运站、跳转页的排名。

这个方向没有错。它确实能改善一些高频查询，也能让官方站点、媒体站点、政府机构、品牌主页这类导航意图更容易被顶上来。

但改善幅度有限。

原因很朴素：如果候选结果本身没有覆盖到真正有价值的页面，本地重排再努力也只能在一堆不太好的东西里挑一个看起来不那么糟的。`local_index` 也一样，只有抓过、存过、解析过的内容才能被召回；没有进入本地视野的页面，依然不存在。

于是我们很自然地走向了下一步：那就自己爬。

## 第二轮补救：引入 Apache Nutch

自建搜索引擎讲到爬虫，很难绕开 [apache/nutch](https://github.com/apache/nutch)。Nutch 是老牌开源爬虫项目，能处理种子 URL、抓取、解析、链接发现、CrawlDB、索引写入等流程，看起来正适合给 `searchme` 补一个本地网页发现层。

当时的实验方案大致是：

- 准备一组种子站点，例如政府、媒体、搜索入口、品牌、学术站点；
- 使用 Nutch 从种子 URL 开始抓取；
- 通过 HTML/Tika 解析正文；
- 通过链接关系继续发现新页面；
- 把结果写入 Solr、Kafka 或归档流程；
- 再由 `searchme` 查询本地索引，与 SearXNG 结果合并重排。

配置上也做了比较克制的限制：单主机抓取、每个 host 控制并发、设置抓取延迟、限制内容大小、过滤常见静态资源和登录页，避免它变成一台没有礼貌的小型噪音制造机。

理论上，这条路可以解决 SearXNG 召回不足的问题。实际上，它让我们更清楚地看到了另一个现实：自建爬虫不是“按下按钮，互联网进碗里来”。

## Nutch 很强，但它不会凭空认识世界

Nutch 的行为非常诚实：你给它种子，它从种子出发；页面里有外链，它沿着外链走；没有外链，它就不知道外面还有什么。

这意味着它天然更擅长爬“已知名单”和“已知名单能链接出去的世界”。如果一个新站点没有被种子覆盖，也没有被当前抓取到的页面链接到，它就不会魔法般出现。

更麻烦的是，今天的大部分网站并不欢迎陌生爬虫：

- 有的网站依赖 JavaScript 渲染，普通抓取拿不到有效正文；
- 有的网站需要 Cookie、地区、登录态或验证码；
- 有的网站通过 robots、WAF、频率限制直接拒绝；
- 有的网站只对已验证的大型爬虫放行；
- 有的网站能抓，但抓回来的是模板、推荐流、广告位和一堆无关链接。

这时再回头看“自建搜索引擎”这几个字，会觉得它们每个字都很轻，合在一起却很重。

真正成熟的搜索引擎不只是爬虫加索引。它还需要持续抓取调度、反垃圾、正文抽取、语言识别、重复检测、链接图、站点评级、时效性判断、法律和 robots 合规、资源预算、失败重试，以及最难的：知道什么内容值得被看见。

## 为什么最后又回到了 SearXNG

最后 `search.js.gripe` 回到 SearXNG，并不是因为我们把 SearXNG 改造成了一个多聪明的搜索引擎。恰恰相反：目前线上采用的是几乎一键搭建的原版 SearXNG，没有对它做大改。

这个决定有点反高潮，但很现实。

自建爬虫方案需要长期维护抓取、解析、索引、调度和反滥用；本地重排方案又绕不开候选集质量的问题。相比之下，原版 SearXNG 至少稳定、轻量、可替换，而且不会把维护成本突然扩张成一个专职岗位。

目前做的主要调整不是改搜索核心，而是把它变得更适合被工具和 LLM 使用：对公共访问开放 JSON 抓取能力，让守规矩的自动化工具可以拿到结构化结果，而不是只能解析 HTML 页面。

当然，公共开放不等于无限开放。对明显不尊重站点边界、抓取行为不克制、或者绕过正常访问约定的客户端，仍然需要限制。比如 Claude 这类在抓取伦理上让人很难放心的访问方，就不应该默认享受同等便利。

换句话说，当前路线不是“自建搜索引擎成功了”，而是“承认搜索核心先交给 SearXNG，自己只维护一个可公开、可控、对 LLM 友好的搜索入口”。

## Codex 的建议，以及我为什么先不做

这里可以插一段署名为 Codex 的建议。

Codex 当时给出的方向是：既然 SearXNG 的抓取质量不高，但仍然能提供候选结果，那就不要继续魔改 SearXNG 本体，而是在外面加一层很薄的 `searchme` JSON gateway。

这层 gateway 可以保持 SearXNG 原样运行，只做结构化输出、缓存、限流、客户端策略，以及一些轻量的 URL 状态标记。例如给 LLM 返回标题、链接、摘要、来源、时间、语言、抓取状态、是否可能是跳转页、是否可能不可访问等字段。它也可以异步检查少量 404，或者把已经成功抓取过的页面留作本地记忆。

这个建议从工程角度是成立的：SearXNG 继续负责“搜一下”，`searchme` 负责“把结果变得更适合 LLM 读取”。如果未来要接 Nutch、StormCrawler、Common Crawl、RSS 或站点地图，也可以把它们作为新的候选来源，而不是再次推翻整个系统。

但我现在暂时不准备加筛选功能。

原因也很简单：之前已经试过筛选、降权和本地重排，结果经常是搜索结果几乎被筛没了。看起来页面更干净，实际上可用信息也被一起清掉了。搜索质量不高是一种问题，但过早替用户判断“哪些结果不该出现”，也可能变成另一种问题。

所以当前更想保留的是一个对 LLM 友好但质量并不完美的环境：结果可以乱一点、脏一点、参差一点，但先让用户和 LLM 接触到它，再自己判断、比较、追问、排除。

这有点像网络开放的问题。总有人担心用户接触到不完美的信息环境，于是想先替他们关掉、筛掉、挡掉。但人总有一天会接触到复杂的信息，并尝试用自己的方式理解它。那个过程不一定漂亮，甚至经常笨拙，可迈出第一步本身就值得肯定。

因此现阶段的 `search.js.gripe` 不追求替用户做最终判断。它只负责提供一个公开、结构化、对 LLM 友好的入口。至于结果好不好、该信哪条、该继续追哪条，先交还给用户和 LLM。

## 入门到放弃，放弃的是什么

这次“从自建搜索引擎入门到放弃”，放弃的不是搜索服务本身，而是放弃那个很诱人的误会：

> 只要有一个开源爬虫、一个索引库、一个搜索框，就能拥有自己的搜索引擎。

更现实的结论是：

小团队或个人站点适合做“搜索入口”和“开放接口”，不适合硬扛“全网搜索基础设施”。把 SearXNG 先跑起来，把 JSON 先开放出来，把判断权先交还给用户和 LLM，反而更接近当前资源条件下的最优解。

这听起来没有“我自己爬完整个互联网”那么热血，但它更能活下来。

而技术项目里，能活下来，有时候已经是一种高级相关性排序。
