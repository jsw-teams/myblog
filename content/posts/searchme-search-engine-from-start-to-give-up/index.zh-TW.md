這篇文章本來可以叫《如何優雅地自架一個搜尋引擎》，但寫到最後才發現，最優雅的地方大概是：知道什麼時候該停手。

`searchme` 的目標並不誇張：做一個面向日常研究、新聞素材、文獻搜尋和影片腳本準備的搜尋入口。它不想複製 Google，也不想假裝一台小伺服器可以吞下整個網際網路。它只是希望在 `search.js.gripe` 上提供一個能用、可控、結果不要太離譜的搜尋體驗。

然而搜尋這件事，越做越像是在碰一套世界觀：你以為自己在做輸入框，實際上是在處理資訊秩序。

**目前可用入口：** `search.js.gripe` 現在正常運作，入口是 <https://search.js.gripe/>。它目前就是一個盡量維持原版的 SearXNG 搜尋站點，並開放 JSON 結果，方便使用者、腳本和守規矩的 LLM 讀取。

給一般使用者最簡單的用法是：先在網頁上正常搜尋；如果要讓支援連網存取的 LLM 抓取結構化結果，就把搜尋詞放進下面這個網址：

```text
https://search.js.gripe/search?q=你的搜尋詞&format=json
```

例如：

```text
https://search.js.gripe/search?q=SearchMe%20SearXNG&format=json
```

然後可以直接對 LLM 說：

```text
請存取這個 JSON 搜尋結果，幫我比較前幾條連結的相關性，並說明哪些結果值得繼續打開：
https://search.js.gripe/search?q=SearchMe%20SearXNG&format=json
```

如果搜尋詞裡有中文或空格，瀏覽器通常會自動處理；不放心的話，可以先在 `search.js.gripe` 網頁裡搜尋，再把網址列裡的查詢改成帶 `format=json` 的形式。

## 起點：先從 SearXNG 開始

最初的方案很直接：既然 [SearXNG](https://github.com/searxng/searxng) 已經是成熟的自架元搜尋專案，那就先拿它當底座。它能聚合多個上游搜尋引擎，部署成本相對可控，也很適合作為自架搜尋入口。

於是 `searchme` 的第一階段，是圍繞 SearXNG 做包裝：前端、API、模式切換、快取、結果清洗、去重，以及一些更貼近自己使用情境的排序策略。

公開倉庫 [jsw-teams/searchme](https://github.com/jsw-teams/searchme) 目前也把 SearXNG 定位成「粗召回」元件：它負責先把候選結果拿回來，但不負責最終品質判斷。換句話說，SearXNG 很適合當一張網，但網到什麼魚，還得自己分揀。

問題也正是從這裡開始。

## 現實：搜尋結果不是髒，是很有生命力

一開始我們以為搜尋品質不好，是因為排序還不夠聰明。後來才發現，排序只是最後一層體面，前面的候選集已經很熱鬧了。

實際爬取和聚合結果裡，會混進很多奇妙內容：

- 標題看起來相關，正文幾乎無關；
- 搜尋詞只出現在導覽列、頁尾或推薦區；
- 同一篇內容被轉載、搬運、聚合成好幾個版本；
- 短網址、跳轉頁、登入頁、入口網站頁面擠在正常結果中間；
- 有些頁面甚至已經是 404，但仍然會被抓到，或被快取裡的舊線索帶出來。

這時才會意識到，「搜得到」不等於「搜得對」。搜尋引擎真正難的不是回傳十條連結，而是在十條連結裡少放幾條看起來像答案、點進去卻讓人開始懷疑人生的東西。

## 第一輪補救：權重排序、記憶體寫入和 local_index

既然 SearXNG 拿回來的結果不夠穩，那就給 `searchme` 加一層自己的判斷。

這一階段做了幾類改進：

1. 權重排序：按語言、網域、來源可信度、頁面類型、短網址風險、官方網站意圖等因素重新打分。
2. 記憶體寫入：把已經看過、判斷過、效果不錯或效果很差的結果留在本地記憶裡。
3. `local_index`：對抓取過的頁面內容做本地快取和召回實驗，讓後續搜尋不只依賴上游搜尋回傳的標題和摘要。
4. 去重和過濾：正規化 URL，合併重複頁面，降低低價值網站、搬運站、跳轉頁的排名。

這個方向沒有錯。它確實能改善一些高頻查詢，也能讓官方網站、媒體網站、政府機構、品牌首頁這類導覽意圖更容易被頂上來。

但改善幅度有限。

原因很樸素：如果候選結果本身沒有覆蓋到真正有價值的頁面，本地重排再努力，也只能在一堆不太好的東西裡挑一個看起來沒那麼糟的。`local_index` 也一樣，只有抓過、存過、解析過的內容才能被召回；沒有進入本地視野的頁面，依然不存在。

於是我們很自然地走向下一步：那就自己爬。

## 第二輪補救：引入 Apache Nutch

自架搜尋引擎講到爬蟲，很難繞開 [apache/nutch](https://github.com/apache/nutch)。Nutch 是老牌開源爬蟲專案，能處理種子 URL、抓取、解析、連結發現、CrawlDB、索引寫入等流程，看起來正適合給 `searchme` 補一個本地網頁發現層。

當時的實驗方案大致是：

- 準備一組種子網站，例如政府、媒體、搜尋入口、品牌、學術網站；
- 使用 Nutch 從種子 URL 開始抓取；
- 透過 HTML/Tika 解析正文；
- 透過連結關係繼續發現新頁面；
- 把結果寫入 Solr、Kafka 或歸檔流程；
- 再由 `searchme` 查詢本地索引，與 SearXNG 結果合併重排。

配置上也做了比較克制的限制：單主機抓取、控制每個 host 的併發、設定抓取延遲、限制內容大小、過濾常見靜態資源和登入頁，避免它變成一台不太有禮貌的小型噪音製造機。

理論上，這條路可以解決 SearXNG 召回不足的問題。實際上，它讓我們更清楚地看到另一個現實：自架爬蟲不是「按下按鈕，網際網路就進碗裡來」。

## Nutch 很強，但它不會憑空認識世界

Nutch 的行為非常誠實：你給它種子，它從種子出發；頁面裡有外連，它沿著外連走；沒有外連，它就不知道外面還有什麼。

這意味著它天然更擅長爬「已知名單」和「已知名單能連出去的世界」。如果一個新網站沒有被種子覆蓋，也沒有被目前抓到的頁面連到，它就不會憑空出現。

更麻煩的是，今天的大部分網站並不歡迎陌生爬蟲：

- 有的網站依賴 JavaScript 渲染，普通抓取拿不到有效正文；
- 有的網站需要 Cookie、地區、登入狀態或驗證碼；
- 有的網站透過 robots、WAF、頻率限制直接拒絕；
- 有的網站只對已驗證的大型爬蟲放行；
- 有的網站能抓，但抓回來的是樣板、推薦流、廣告位和一堆無關連結。

這時再回頭看「自架搜尋引擎」這幾個字，會覺得每個字都很輕，合在一起卻很重。

真正成熟的搜尋引擎不只是爬蟲加索引。它還需要持續抓取調度、反垃圾、正文抽取、語言識別、重複偵測、連結圖、網站評級、時效性判斷、法律和 robots 合規、資源預算、失敗重試，以及最難的：知道什麼內容值得被看見。

## 為什麼最後又回到了 SearXNG

最後 `search.js.gripe` 回到 SearXNG，並不是因為我們把 SearXNG 改造成了多聰明的搜尋引擎。剛好相反：目前線上採用的是幾乎一鍵架好的原版 SearXNG，沒有對它做大改。

這個決定有點反高潮，但很現實。

自架爬蟲方案需要長期維護抓取、解析、索引、調度和反濫用；本地重排方案又繞不開候選集品質的問題。相比之下，原版 SearXNG 至少穩定、輕量、可替換，而且不會把維護成本突然擴張成一個專職工作。

目前主要調整不是改搜尋核心，而是讓它更適合被工具和 LLM 使用：對公共存取開放 JSON 抓取能力，讓守規矩的自動化工具可以拿到結構化結果，而不是只能解析 HTML 頁面。

當然，公共開放不等於無限制開放。對明顯不尊重站點邊界、抓取行為不克制，或繞過正常存取約定的客戶端，仍然需要限制。像 Claude 這類在抓取倫理上讓人很難放心的存取方，就不應該預設享有同等便利。

下面這張截圖就是很典型的現場：一邊要求別人尊重規則，一邊自己抓取時毫不客氣。說得直白一點，真是不知羞恥。

![不受歡迎的抓取行為截圖](https://files.js.gripe/files/raw/fil_AFcHWSmTpO_GAPUQE6LPXm7A.png)

換句話說，現在的路線不是「自架搜尋引擎成功了」，而是「承認搜尋核心先交給 SearXNG，自己只維護一個公開、可控、對 LLM 友善的搜尋入口」。

## Codex 的建議，以及我為什麼先不做

這裡可以插一段署名為 Codex 的建議。

Codex 當時給出的方向是：既然 SearXNG 的抓取品質不高，但仍然能提供候選結果，那就不要繼續魔改 SearXNG 本體，而是在外面加一層很薄的 `searchme` JSON gateway。

這層 gateway 可以保持 SearXNG 原樣運行，只做結構化輸出、快取、限流、客戶端策略，以及一些輕量的 URL 狀態標記。例如給 LLM 回傳標題、連結、摘要、來源、時間、語言、抓取狀態、是否可能是跳轉頁、是否可能無法存取等欄位。它也可以非同步檢查少量 404，或者把已經成功抓取過的頁面留作本地記憶。

這個建議從工程角度是成立的：SearXNG 繼續負責「搜一下」，`searchme` 負責「把結果變得更適合 LLM 讀取」。如果未來要接 Nutch、StormCrawler、Common Crawl、RSS 或站點地圖，也可以把它們作為新的候選來源，而不是再次推翻整個系統。

但我現在暫時不準備加篩選功能。

原因也很簡單：之前已經試過篩選、降權和本地重排，結果經常是搜尋結果幾乎被篩沒了。看起來頁面更乾淨，實際上可用資訊也被一起清掉了。搜尋品質不高是一種問題，但太早替使用者判斷「哪些結果不該出現」，也可能變成另一種問題。

所以目前更想保留的是一個對 LLM 友善、但品質並不完美的環境：結果可以亂一點、髒一點、參差一點，但先讓使用者和 LLM 接觸到它，再自己判斷、比較、追問、排除。

這有點像網路開放的問題。總有人擔心使用者接觸到不完美的資訊環境，於是想先替他們關掉、篩掉、擋掉。但人總有一天會接觸到複雜的資訊，並嘗試用自己的方式理解它。那個過程不一定漂亮，甚至常常笨拙，可邁出第一步本身就值得肯定。

因此現階段的 `search.js.gripe` 不追求替使用者做最終判斷。它只負責提供一個公開、結構化、對 LLM 友善的入口。至於結果好不好、該信哪一條、該繼續追哪一條，先交還給使用者和 LLM。

## 入門到放棄，放棄的是什麼

這次「從自架搜尋引擎入門到放棄」，放棄的不是搜尋服務本身，而是放棄那個很誘人的誤會：

> 只要有一個開源爬蟲、一個索引庫、一個搜尋框，就能擁有自己的搜尋引擎。

更現實的結論是：

小團隊或個人站點適合做「搜尋入口」和「開放介面」，不適合硬扛「全網搜尋基礎設施」。把 SearXNG 先跑起來，把 JSON 先開放出來，把判斷權先交還給使用者和 LLM，反而更接近目前資源條件下的最優解。

這聽起來沒有「我自己爬完整個網際網路」那麼熱血，但它更能活下來。

而技術專案裡，能活下來，有時候已經是一種高級的相關性排序。
