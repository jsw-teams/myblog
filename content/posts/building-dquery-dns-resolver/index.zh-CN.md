DNS 看起来像互联网里最朴素的一环：给一个域名，拿一个地址。真正把解析器做成公开服务后，才会发现它夹在很多边界之间：隐私、缓存、区域合规、污染、拦截、上游选择、前端展示、控制台账户，以及一个小但很要命的细节：DNS 报文里的 ID 每次都可能不同。

`dquery.js.gripe` 这次重构的目标，是把一个能用的 DNS-over-HTTPS 查询入口整理成可维护的解析器服务。它既提供公开查询，也提供个人 UUID 解析路径；既能查询，也能按规则对特定域名不解析或拦截；既要减少源站压力，也不能为了缓存命中牺牲 DNS 协议准确性。

<!--more-->

## 为什么要做自己的解析器

DoH 解决的是“本机到解析器之间”的明文 DNS 暴露问题。它把 DNS 查询放进 HTTPS 里，局域网、运营商链路和公共 Wi-Fi 不再轻易看到你正在查询哪个域名。

但这不等于 DNS 查询突然消失。解析器仍然会看到问题本身：你问了哪个主机名、问的是 A 还是 AAAA、查询来自什么区域、是否带 ECS，等等。换句话说，把 DNS 换成 DoH 后，信任对象从沿路网络设备转移到了 DoH 提供商。

这也是自建解析器的意义：至少你知道查询日志、缓存策略、拦截逻辑和上游选择是怎样被实现的，而不是把所有行为交给一个黑盒。

## 入口：公开查询和个人 UUID

这次我们把查询入口收敛到两个形式：

```text
https://dquery.js.gripe/dns-query
https://dquery.js.gripe/dns-query/{resolver_uuid}
```

公开入口适合普通网页查询、临时测试和不带个人规则的 DoH 使用。个人入口使用成熟 UUID，而不是早期 `usr_...` 这类路径。UUID 不代表“加密身份”，它只是一个稳定、可管理、不会暴露内部用户 ID 的解析器标识。

个人路径背后绑定本地账户体系。控制台登录后会显示自己的 DoH 地址，并管理规则、拦截模式、日志和 profile。SSO 更适合作为外部身份绑定，而不是把外部账户体系直接混进解析器内部账户模型。

## 对特定域名不解析或拦截

解析器不仅是“转发器”。它也可以在本地做决策。

比如某个用户希望对一批域名执行阻断，dquery 会在真正回源之前检查个人规则和规则集。如果命中 block 策略，可以直接返回 NXDOMAIN，也可以返回指向阻断页的响应。这样做有几个好处：

1. 策略在本地执行，不需要把所有判断交给上游 DNS。
2. 命中阻断的域名不会继续向上游泄露。
3. 不同个人 profile 可以有不同规则，而不是全站一把尺子。

这类“本地不解析”并不是为了伪装网络状态，而是为了让用户知道：哪些域名是自己明确选择不解析，哪些是上游返回结果，哪些是区域策略导致不可用。

## DNS 提供商仍然能看到主机名

很多人把 DoH 理解成“DNS 隐私的终点”，这其实太乐观。DoH 只是保护传输链路，不会让解析器不知道你问了什么。

如果你使用第三方 DNS 服务，对方理论上能看到查询主机名。更进一步，如果解析链路上存在强制污染、劫持或策略性拦截，用户收到的结果可能不是权威 DNS 本来的结果。现实里常见的例子包括反诈拦截、运营商级域名重定向、地区性 DNS 污染，以及某些公共解析服务在特定地区配合返回被改写的答案。

这不是抽象风险。2010 年，中国数字时代转载报道提到，DNS 污染曾影响到中国境外，Netnod 维护的中国根服务器镜像一度被撤回路由通告、与国际互联网切断连接。更准确地说，这不是“中国控制根服务器后被取消资格”，而是根服务器镜像因为异常影响被从全球路由中隔离。参见：[DNS污染问题发生后中国关闭根服务器](https://chinadigitaltimes.net/chinese/54479.html)。

2014 年中国大陆大规模网络异常也常被拿来讨论 DNS 污染的风险。相关条目记录，当时大量域名被解析到同一错误 IP，外界对原因有不同说法，其中一种调查方向认为这与防火长城的 DNS 污染配置有关。参见：[2014年中国大陆网络异常事件](https://zh.wikipedia.org/zh-hans/2014%E5%B9%B4%E4%B8%AD%E5%9B%BD%E5%A4%A7%E9%99%86%E7%BD%91%E7%BB%9C%E5%BC%82%E5%B8%B8%E4%BA%8B%E4%BB%B6)。

这些事件给解析器设计留下的经验很简单：DNS 不是绝对中立的管道。上游能看见查询，也可能被要求或被迫改变答案。自建解析器至少要把“谁看见了什么、谁改写了什么、用户为什么拿不到答案”尽量拆开。

## 区域策略：不是所有入口都必须一样

dquery 对公开匿名入口保留区域策略。原因很现实：某些地区对公开 DNS 解析服务有合规要求，尤其当服务被滥用为绕过本地解析策略的公共入口时，运营风险会落到服务提供者身上。

所以我们把前端查询、公开匿名 DoH、个人 UUID DoH 分开处理。前端查询更像网页工具，不应该因为初始化状态或区域判断就不可用；公开匿名 DoH 可以按地区返回 451；个人 UUID 入口则更强调账户、规则和 profile 绑定。

这不是一个完美答案，但它让不同使用场景的边界更清楚。

## 缓存：DNS ID 是一个小陷阱

DNS wire message 里有一个 request ID。很多客户端每次查询都会换一个 ID。问题来了：如果只按完整 `dns=` 参数做 CDN 缓存，即使查询的是同一个域名、同一个类型，只要 ID 不同，URL 就不同，CDN 就会认为它们是不同对象。

最初我们尝试把归一化放在 Worker 上：解析 `dns=` 参数，把 DNS ID 清零后构造缓存键，命中时再把响应 ID 改回当前请求的 ID。这个方案命中率很好，但每个 UUID DoH 请求都会消耗 Worker 请求数。对于 DNS 这种高频入口，额度压力会很快变成主要问题。

后来我们把正式链路切回源站：Worker 路由移除，归一化交给 Go 后端。后端缓存键不包含 DNS ID，但返回缓存命中时会把响应 ID 改回当前查询 ID。这个细节很关键：缓存命中不能以牺牲协议准确性为代价。

OpenResty 层也曾做过归一化 `proxy_cache_key`，但它无法在缓存命中时重写 DNS response ID。这样虽然看起来能命中，实际上可能把旧请求的 ID 返回给新请求。最后我们关闭了 DoH 的 OpenResty 代理缓存，让后端负责准确归一化。

## 让 CDN 只缓存源站 HIT

现在的策略是：

```text
源站 MISS/BYPASS -> Cache-Control: no-store
源站 HIT/STALE  -> Cache-Control: public, max-age=..., s-maxage=...
```

Cloudflare Cache Rule 只负责把 `/dns-query` 及其子路径纳入缓存范围，并遵循源站缓存头：

```text
(http.host eq "dquery.js.gripe" and http.request.method eq "GET" and starts_with(http.request.uri.path, "/dns-query"))
```

这样第一轮请求会进入源站，由 Go 后端解析并填充本地归一化缓存；第二轮同域名、不同 DNS ID 的请求会在源站命中，源站返回正确 response ID，并允许 CDN 缓存这个具体 URL；后续相同 URL 才能由 Cloudflare 直接 HIT。

这不是“让 CDN 理解 DNS wire message”。CDN 仍然只认识 URL。真正的 DNS 归一化在源站完成，CDN 只缓存源站已经确认安全共享的结果。

## 最后的状态

这次重构后，dquery 的核心边界更清楚：

- `/dns-query` 是公开 DoH 查询入口。
- `/dns-query/{uuid}` 是个人解析器入口。
- 个人规则可以对域名执行允许、阻断、NXDOMAIN 或阻断页逻辑。
- 匿名入口可以按区域策略拒绝。
- Worker 不在正式 DoH 链路上消耗请求数。
- Go 后端负责 DNS ID 归一化缓存，并在 HIT 时重写 response ID。
- CDN 只缓存源站已经标记为 HIT/STALE 的响应。

DNS 服务很容易被做成一个“能返回答案”的小程序。真正难的是承认它处在信任、合规和协议细节的交界处。解析器不是只要快就好，它还要能解释自己的行为：为什么解析、为什么不解析、为什么拦截、为什么缓存，以及缓存命中时有没有仍然返回正确的 DNS 报文。
