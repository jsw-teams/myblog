DNS 看起来像互联网里最朴素的一环：给一个域名，拿一个地址。

很多人第一次理解 DNS，都会把它当成“互联网电话簿”。这个比喻没有错，但只说了一半。电话簿至少还摆在你面前，而 DNS 查询通常发生在你看不见的地方：打开网页、启动 App、同步邮件、访问 API、拉取系统更新，背后都可能先问一句：“这个名字对应哪台服务器？”

如果这句话是明文传输，沿途网络设备可能看见它。如果解析器本身有策略，它也可能改变答案。如果缓存做错，解析器甚至可能为了性能返回一个协议上不够正确的 DNS 报文。

dquery 仍处在小规模测试和持续完善阶段，所以本文不会提供具体服务路径、查询入口或公开接入说明。这里更想记录的是一次自建递归解析器的工程经历：我们怎样拆分匿名查询、个人配置、控制台和本地规则；怎样处理 DoH 的缓存陷阱；又怎样在隐私、性能、合规和协议正确性之间做取舍。

## DNS 为什么会变成信任问题

传统 DNS 主要跑在 UDP/53 上。它简单、快、兼容性好，所以几十年来一直是互联网的基础组件。但它诞生得很早，默认没有加密，也没有很好地防止路径上的第三方观察和篡改。

这意味着，在一些网络环境中，DNS 查询可能被运营商、公共 Wi-Fi、网关设备、中间盒或其他路径观察者看到。更糟糕的情况下，攻击者还可能抢先返回伪造结果，让用户以为自己拿到了正常答案。

后来出现的 DoT、DoH、DoQ，本质上都是在修补这个历史包袱：

- DoT 把 DNS 放进 TLS 连接，协议边界清楚。
- DoH 把 DNS 放进 HTTPS，更容易接入浏览器和 CDN 生态。
- DoQ 把 DNS 放进 QUIC，希望在加密、低延迟、连接迁移和丢包恢复之间取得更好平衡。
- ODoH 进一步尝试把“谁在问”和“问了什么”拆开，让代理知道用户来源，但看不到查询内容；目标解析器能解密查询，但不直接看到用户 IP。

不过，加密 DNS 很容易被误解成“从此完全匿名”。这并不准确。DoH 主要保护的是客户端到解析器之间这段链路。路上的人更难直接看到和修改 DNS 查询，但解析器本身仍然会看到你问了哪个域名、问的是什么记录类型、请求大概来自哪里、是否命中规则，以及最终选择了哪个上游。

换句话说，DoH 不是让 DNS 隐私问题消失，而是把信任对象从“沿途所有网络设备”缩小到“你选择的解析器”。自建解析器的价值也正在这里：至少日志策略、上游选择、缓存行为、拦截规则和区域边界可以由自己定义，并且能向用户解释。

## 先把几个常见误解拆开

讨论 DNS 时，最容易把几件事混在一起：根服务器、国家顶级域名、递归解析器、运营商劫持、公共 DNS、加密 DNS。这些都和 DNS 有关，但它们不在同一层。

根服务器负责告诉递归解析器：“`.com` 应该去问谁，`.cn` 应该去问谁，`.iq` 应该去问谁。”它不负责回答每一个具体网站的最终 IP。普通用户日常访问网站时，更多接触的是本机缓存、路由器、运营商递归解析器、公共 DNS、DoH 解析器和权威 DNS。

所以，“根服务器系统是否稳定”和“用户日常拿到的 DNS 答案是否中立”，是两个相关但不同的问题。

### 根服务器问题要放回正确层级

早期中文互联网里，经常能看到一种说法：“中国没有根服务器，所以如果被美国制裁，域名系统可能一夜失效。”这类说法有历史背景，但表述过于粗糙。

准确一点说，DNS 根服务器系统有 13 个根服务器标识，从 A-root 到 M-root，由多个独立运营方管理。IANA 的根服务器列表可以看到这些标识和运营方；Root Server Technical Operations Association 也说明，13 个根标识通过 anycast 分布到全球很多实例。

这里至少要区分四层：

- 根服务器标识运营权：谁负责运营 A-root 到 M-root 这些逻辑根标识之一。
- 根服务器实例：某个根标识在全球不同地点部署的 anycast 节点。
- 国家顶级域名管理权：谁负责 `.cn`、`.iq`、`.ly` 这样的 ccTLD 注册局和权威 DNS。
- 递归解析路径：普通用户查询域名时，实际用了哪个递归解析器，经过了哪些缓存和网络路径。

早期舆论常常把这几层合在一起讲，于是“没有根标识运营权”被说成“没有根服务器”，“国家顶级域管理异常”被说成“根服务器让一个国家消失”，“运营商路径污染”又被说成“根区被改写”。这会让讨论变得很吓人，但技术上并不准确。

伊拉克 `.iq` 和利比亚 `.ly` 更像是国家顶级域治理、权威 DNS、技术联系人和运营连续性问题。它们能提醒我们 ccTLD 治理很重要，但不应该被简化成“根服务器一键让国家消失”。更完整的根区、ICANN、司法辖区和网络主权争议，放到后面的“茶后闲谈”里再展开。

### DNS 答案不总是中立的

很多人以为 DNS 就像查字典：字典里是什么，答案就是什么。但现实中的 DNS 解析链路很长，答案可能在不同层级被改变。

这种改变不一定都来自政治审查，也可能来自商业策略、安全产品、家长控制、企业内网策略、恶意劫持，或者单纯的错误配置。

2003 年，VeriSign 推出过 Site Finder。用户访问不存在的 `.com` 或 `.net` 域名时，正常 DNS 语义应该返回“这个名字不存在”。但 Site Finder 会把这些不存在的域名导向一个搜索页面。这个设计引发了很大争议，因为许多程序并不只是在浏览器里“打开网页”：邮件系统、反垃圾规则、自动化脚本和网络设备也会依赖 NXDOMAIN 这个语义。

2014 年土耳其封锁 Twitter 和 YouTube 时，也发生过公共 DNS 被拦截的案例。许多用户把 DNS 改成 Google Public DNS，希望绕过本地解析限制；随后 Google 表示当地网络中出现了伪装成 Google DNS 的服务器，用来阻断相关服务。这说明公共 DNS 不是魔法开关。只要查询仍然走明文或路径可被接管，中间网络仍然可能拦截、冒充或阻断它。

再看更大范围的研究，GFWatch 对中国大陆 DNS 过滤做过长期测量。USENIX Security 2021 论文《How Great is the Great Firewall? Measuring China's DNS Censorship》介绍了一个大规模、长期的 DNS 过滤测量平台，并观察到 DNS 过滤、伪造记录注入，以及部分公共解析器缓存受到污染的现象。

对 dquery 这类自建解析器来说，这些案例的启发不是简单得出某个政治结论，而是提醒我们：DNS 结果可能受到路径、上游和缓存的共同影响，解析器需要尽可能区分这些来源。

## 我们要做的不是黑盒解析器

一个公开 DNS 服务，如果只返回答案，却不解释答案从哪里来，就很容易变成新的黑盒。

dquery 的目标不是做一个神秘的“万能 DNS”，而是把解析过程拆成几个可以理解的步骤：

```text
客户端请求
  -> 入口判断：匿名、个人或控制台
  -> 区域与账户策略
  -> 本地域名规则
  -> 归一化缓存
  -> 上游递归解析
  -> 返回 DNS 响应
```

这样做的好处是，每一次结果都尽量有来源：

- 如果域名被用户规则阻断，应该能说明这是本地规则命中。
- 如果域名返回 NXDOMAIN，应该区分它是上游真实返回，还是本地规则主动返回。
- 如果匿名入口因区域策略不可用，应该明确返回对应 HTTP 状态，而不是伪装成服务故障。
- 如果结果来自缓存，也应该保证 DNS 报文仍然符合协议，而不是为了命中率牺牲正确性。

这听起来像细节，但这些细节决定了解析器能不能被信任。

## 本地规则：不是所有域名都需要问上游

解析器不一定只是上游 DNS 的传声筒。在真正回源之前，dquery 会先检查用户 profile 和规则集。

如果某个域名命中本地策略，解析器可以选择：

- 正常放行，继续查询上游。
- 返回 NXDOMAIN，表示这个名字不存在。
- 返回阻断页地址，让用户知道它被拦截。
- 返回策略错误，提示这是规则或区域限制导致的结果。

这类本地预处理有几个实际意义。

第一，它可以减少不必要的上游查询。广告、追踪、恶意域名如果已经被用户明确加入阻断规则，就没有必要再把请求交给第三方递归解析器。

第二，它减少了被阻断域名的外泄。被本地规则处理的域名，不会继续暴露给上游 DNS 服务。

第三，它允许“千人千面”。不同个人配置可以绑定不同 profile：有人希望只拦截恶意域名，有人希望额外拦截广告和追踪，有人则希望尽量保持原始解析。公开解析器如果只有一份全局规则，很难兼顾这些需求。

但这里也要保持克制。解析器不应该偷偷改答案，更不应该让用户误以为所有结果都来自权威 DNS。只要发生本地处理，就应该在日志、控制台或可观测信息中留下清楚说明。

## 区域策略：明确拒绝比假装故障更好

公开 DNS 服务还会碰到合规和滥用问题。

某些地区对公共解析服务、加密 DNS 或绕过本地解析策略的入口有不同要求。如果一个匿名 DoH 入口被大规模滥用，风险最终会落到服务提供者身上。

因此，我们把几类入口拆开：

- 前端查询页面：更像网页工具，应该尽量稳定可用。
- 匿名解析入口：适合基础公共查询，但可以根据区域策略拒绝服务。
- 个人解析入口：和账户、profile、规则、配额绑定，更适合长期使用。
- 控制台入口：用于管理规则、查看状态和配置个人解析器。

如果匿名入口在某些地区不可用，我们更倾向于返回 HTTP 451，而不是含糊地返回 403、502 或直接超时。451 的含义是“因法律原因不可用”。它至少告诉用户：服务不是坏了，也不是解析器崩了，而是这个入口在当前条件下不能交付。

这里尤其包括中国大陆。原因不是技术上做不到，而是合规成本和治理风险都太高。公共递归解析器一旦面向中国大陆提供服务，就很容易被要求接入本地监管和内容治理链条：日志留存、滥用处置、域名处置、甚至对特定域名返回策略性结果。对大型公共 DNS 服务商来说，这可能被包装成“合规运营”；但对我们来说，这会让解析器从“尽量解释答案从哪里来”，滑向“在源头上配合改写答案”。

这也是我们不希望 dquery 在当前阶段向中国大陆开放解析器服务的原因。一个解析器如果为了进入某个市场而必须变成不中立的上游，那它就不再只是保护客户端到解析器之间的链路，而是在递归解析源头制造另一层污染。国内一些公共解析服务在特定域名上返回策略性答案，本质上也接近这个问题：加密传输保护了“到解析器为止”的路，却不能保证解析器本身不参与改写。

2010 年 I-root 中国节点事件也给了类似提醒。当时部分境外网络因为路由和任播路径问题，拿到了异常 DNS 回答；后续公开报道提到，相关中国节点的路由通告被撤回以避免影响继续扩散。这个案例并不是“根服务器让一个国家消失”，而是说明：本地 DNS 策略、任播节点和 BGP 路由一旦叠在一起，本来局部的污染或错误答案可能外溢到更大范围。对自建递归解析器来说，最稳妥的边界就是不要进入自己无法保持中立和可解释性的合规环境。

这不是完美答案，但比沉默更诚实。

## 缓存真正麻烦的地方：DNS ID

DNS 是高频服务。没有缓存，源站压力会很大，延迟也会升高。但 DNS 的缓存又不能像普通网页那样粗暴处理，因为 DNS 报文本身有协议细节。

一个关键字段是 Transaction ID，也就是 DNS 报文头部最前面的 16 位 ID。RFC 1035 定义了 DNS 报文格式，其中头部包含用于匹配查询和响应的 ID 字段。客户端发起查询时通常会生成一个 ID，响应必须把这个 ID 带回来，客户端才能确认“这个答案对应我刚才那次请求”。

DoH 的 GET 请求会把 DNS wire message 经过 Base64URL 编码后放进 URL 参数里。RFC 8484 明确描述了这种 GET 形式。问题就来了：如果两个客户端查询同一个域名、同一个记录类型，但 DNS ID 不同，那么编码出来的参数也不同。CDN 看到的是两个不同 URL，自然会把它们当成两个不同缓存对象。

协议文档其实已经注意到这个问题，并建议 DoH 客户端在某些格式下使用 ID=0，以提高 HTTP 缓存友好性。但现实中，我们不能假设所有客户端都这么做。

所以，服务端必须自己处理这个问题。

## 为什么不把归一化全部放在边缘脚本

最初我们考虑过把归一化放在边缘脚本上：解析 DoH 请求里的 DNS 报文，把 DNS ID 清零后构造缓存键；命中缓存时，再把响应里的 ID 改回当前请求的 ID。

从协议上看，这个方案可行，缓存命中率也好。但 DNS 查询频率很高，如果每个个人解析请求都经过边缘脚本，请求数和成本很快会变成主要问题。

于是最终设计改成：正式 DoH 链路不依赖边缘脚本做核心协议处理，归一化交给后端完成。

也就是说，后端会把 DNS ID 从缓存键中剥离，但不会忽略其他真正影响答案的因素。一个安全的缓存键，至少要考虑：

- 查询域名。
- 记录类型，例如 A、AAAA、HTTPS、TXT。
- 查询类，通常是 IN。
- 影响结果的 DNS 标志。
- 是否携带 ECS 等会改变答案的扩展信息。
- 当前个人配置或 profile。
- 本地规则版本。
- 区域策略。
- 选择的上游或线路。

这样才能避免一个用户的规则结果被另一个用户误用，也避免不同区域、不同策略、不同上游的结果混在一起。

命中缓存后，后端再把响应报文前两个字节改回当前请求的 DNS ID。这样客户端看到的仍然是协议正确的响应。

这一步看似很小，但它是整个缓存方案的核心：我们可以优化命中率，但不能破坏 DNS 的请求响应匹配机制。

## 反向代理和 CDN 应该做什么

反向代理很适合做 TLS 终止、路由、限流和普通 HTTP 代理。但它不适合作为 DoH 二进制响应的核心改写层。

原因很简单：DoH 响应体是 DNS wire message，缓存命中后仍然需要针对每个请求动态改写前两个字节的 DNS ID。如果在反向代理的 body filter 里硬做，会增加复制和 CPU 成本，也更容易在并发场景中引入难以排查的问题。

所以，我们把职责重新划分：

```text
客户端 DoH 请求
  -> CDN 或边缘网络
  -> 反向代理路由
  -> 后端解析 DNS 报文
  -> 生成不含 Transaction ID、但包含真实语义维度的缓存键
  -> 命中后改回当前请求的 response ID
  -> 返回协议正确的 DNS 响应
```

CDN 仍然有价值，但它不应该负责理解 DNS wire message。它更适合做第二层缓存：只缓存源站明确标记为可共享的响应。

因此我们让源站通过 `Cache-Control` 表达缓存意图：

```text
源站 MISS 或 BYPASS:
Cache-Control: no-store

源站 HIT 或 STALE:
Cache-Control: public, max-age=..., s-maxage=...
```

这样做的意思是：第一次没有命中的请求，不让 CDN 存；源站已经确认可以共享的命中结果，再允许 CDN 缓存；CDN 只遵循 HTTP 缓存语义，不参与 DNS 报文改写。

需要注意的是，CDN 只能缓存它看到的 HTTP 对象。对于随机 DNS ID 导致 URL 不同的客户端，真正稳定提升命中率的仍然是源站归一化缓存。CDN 更像是锦上添花：当 URL 完全相同，或客户端本身使用更缓存友好的 DoH 请求格式时，它才能更明显地放大缓存收益。

## 个人解析入口的意义

匿名入口适合做基础查询，但不适合承载所有功能。个人解析入口的意义，不只是“换一个入口”，而是把解析行为和用户 profile 绑定起来。

匿名入口可以保持最小能力：接受标准 DoH 查询，执行基础限制，必要时按区域策略拒绝。

个人入口则可以支持更细的功能：

- 用户自定义规则。
- 不同设备使用不同 profile。
- 家庭、移动端、服务器分开策略。
- 查询统计和异常观察。
- 配额、限流和滥用控制。
- 将来接入账户系统或 SSO。

这比把所有人都放在同一个全局解析策略里更清晰，也更容易解释问题。

当某个域名解析异常时，我们可以判断：是匿名入口限制、个人规则命中、上游异常、缓存命中、区域策略，还是客户端请求格式本身有问题。

目前这类个人入口和控制台能力仍然在逐步完善中，因此本文只讨论设计边界和工程取舍，不提供具体服务路径或公开接入说明。

## DoH 能保护什么，不能保护什么

到这里可以重新回答一个常见问题：用了 DoH，DNS 提供商还能看到主机名吗？

答案是：能。

DoH 加密的是客户端到 DoH 解析器之间的传输链路。它能防止很多路径上的旁观和篡改，但解析器必须解密请求，才能知道你要查什么，也才能返回答案。

所以，DoH 的主要收益是：

- 公共 Wi-Fi 或中间网络更难直接看到 DNS 查询内容。
- 路径上的旁路抢答和普通 DNS 劫持更难成功。
- 浏览器、系统或应用可以用 HTTPS 基础设施发起 DNS 查询。
- 用户可以选择自己信任的解析器，而不是默认交给接入网络。

但 DoH 不能保证：

- 解析器运营者完全不知道你查了什么。
- 上游返回结果一定中立。
- 所有网络审查或封锁都失效。
- IP 层、SNI、流量特征等其他信息完全隐藏。
- 缓存、日志和账户系统没有新的隐私风险。

这也是为什么解析器要透明。与其宣传“绝对隐私”，不如明确告诉用户：我们保护哪一段，记录什么，不记录什么，哪些结果来自本地规则，哪些结果来自上游。

## 茶后闲谈：根服务器、ICANN 和“网络霸权”的说法

国内讨论 DNS 时，偶尔会看到类似“控制根服务器就控制互联网命脉”“美国可以把某些网站从地球上抹除”的说法。2021 年国内媒体围绕 36 个伊朗相关网站被查封的讨论，就常被放进这类叙事里。

这类说法抓住了一个真实问题：如果域名注册商、注册局、托管服务、CDN 或支付合规服务处在某个国家的司法辖区内，当地法院命令和制裁规则确实可能影响这些域名或服务。但从 DNS 技术层面看，把它直接说成“美国通过根服务器一键抹除网站”，就过度简化了。

2021 年那次事件，更准确地说，是美国司法部门依据法院命令查封了一批具体域名。它影响的是这些域名的注册和解析服务，而不是把伊朗国家顶级域 `.ir` 从根区删除，也不是 ICANN 回收了某个国家顶级域。事实上，一些受影响媒体后来改用 `.ir` 域名继续上线，这也说明事件主要发生在具体域名和司法管辖层面，而不是整个国家顶级域被根区移除。

这里需要把几层拆开：

```text
单个域名查封：
  例如某个 .com 域名被注册商、注册局或法院命令锁定、改指向或接管。

TLD 委派变化：
  根区里某个顶级域的 NS、DS、glue 等委派数据发生变化。

ccTLD 治理问题：
  某个国家顶级域的注册局、权威 DNS、技术联系人或本地治理流程出问题。

根服务器实例：
  全球各地部署的 anycast 节点，负责对外提供同一份根区数据。

递归解析路径：
  普通用户真正使用的运营商 DNS、公共 DNS、DoH 解析器和缓存路径。
```

如果只是查封一个具体域名，根区通常不需要变化，TLD 权威服务器也仍然正常工作。用户看到的是这个具体域名被跳转到查封页、无法解析，或被锁定，但同一个 TLD 下的其他域名不受影响。

如果真的发生 TLD 层面的重新委派，那影响才会进入根区。比如某个 ccTLD 的管理者被更换，根区里的 NS、DS、glue 等数据会更新。根服务器实例随后同步新的根区数据；递归解析器在缓存过期后，会按照新的根区委派去找新的 TLD 权威服务器。旧的 TLD 权威服务器即使还在运行，也不再是公共 DNS 标准路径的一部分。

如果某个 ccTLD 被退休并最终从根区移除，情况更明显：公共根区不再告诉递归解析器“这个 TLD 应该去问谁”。旧权威服务器在技术上仍然可以继续回答直接查询，但普通公共 DNS 链路不会自然走到那里。除非某些网络使用替代根、私有根或固定旧数据，否则这个 TLD 就不再属于全球公共 DNS 的一致命名空间。

所以，对 IANA/ICANN 的态度也不必走向两个极端。一边不能把它们描述成完全没有历史包袱的纯技术乌托邦；另一边也不应该把它们说成某个国家随手关闭互联网的按钮。更准确的理解是：公共 DNS 根区是一套有历史背景、有政治争议、但也有公开流程、问责机制和社区参与结构的全球协调机制。

2016 年 IANA stewardship transition 完成后，美国政府与 ICANN 的 IANA 职能合同已经结束。今天的 ICANN 采用多利益相关方模式，政府、ccTLD 社群、技术社群、注册商、注册局、商业和非商业用户、普通终端用户都可以通过不同组织和委员会参与。它也有 Reconsideration、Independent Review Process、Ombudsman、Empowered Community 等问责机制。它们不能保证这套机制完美无缺，但至少说明公共根区治理不是一条单向命令链。

如果有人质疑“IANA/ICANN 的资料可信吗”，最好的回应不是要求对方相信某个机构，而是把问题变成可验证链条：根区登记可以查，根区文件可以下载，根服务器可以从不同网络测量，DNSSEC 可以验证信任链，ccTLD 重新委派和退休流程有公开文档，第三方学术测量和运营商观测也能交叉印证。

合理的“独立自主”，应该更多放在韧性建设和治理参与上：建设本地递归解析能力、部署根服务器实例、做好缓存、启用 DNSSEC 验证、建立故障应急和测量系统、参与 ICANN、IETF、RIR、ccNSO、GAC 等国际机制。这些都能提高网络韧性。相反，如果另建一套与公共根区不兼容的替代根，让同一个域名在不同网络里指向不同结果，反而会破坏全球互联网最重要的特性：同一个名字在全球大体指向同一套公共命名空间。

所以，那类文章适合用来提醒我们：域名系统确实会受到法律、制裁、注册商、注册局和国际治理结构影响。但它不适合被直接解读成“根服务器一键关闭互联网”。对一个 DoH 解析器来说，真正重要的不是复述阴谋论，也不是假装 DNS 完全中立，而是尽量把答案来源讲清楚：它来自根区委派、TLD 权威、上游递归、本地规则、缓存命中、区域策略，还是某种查封、拦截或污染。

## 茶后坦言：DNS 查询方式还会继续变

DNS 查询方式的演进，基本是一条从“默认信任网络”走向“尽量减少暴露面”的路。

UDP/53 足够快，但它把查询内容暴露给路径。DoT 把 DNS 放进 TLS，协议边界清楚，但独立端口也更容易被识别和策略化。DoH 把 DNS 放进 HTTPS，部署和穿透能力更好，也更适合浏览器生态，但它会把信任集中到解析器。DoQ 试图借助 QUIC 改善延迟和连接迁移。ODoH 则进一步把客户端来源和查询内容拆给不同角色，避免单一服务同时知道“谁在问”和“问了什么”。

ODoH 当然不是免费午餐。它会带来额外延迟、代理可用性、密钥发布、部署复杂度，以及代理和目标解析器是否合谋的问题。它更适合作为长期演进方向，而不是一开始就强行加入核心链路。

对当前阶段的 dquery 来说，更现实的目标是先把普通 DoH 做正确：入口清晰、规则透明、缓存安全、区域策略明确、协议行为可靠。

## 最后的状态

这次重构后，dquery 的边界比以前清楚了很多：

- 匿名入口和个人入口分开。
- 本地规则可以在回源前处理域名。
- 区域策略用明确状态表达，而不是伪装成故障。
- 边缘脚本不再承担正式 DoH 链路中的高频协议处理。
- 后端负责 DNS ID 归一化缓存，并在命中时改回当前请求 ID。
- 缓存键不只排除 DNS ID，还要保留真正影响答案的语义维度。
- CDN 只缓存源站明确标记为可共享的结果。
- 未来可以考虑 ODoH，把用户来源和查询内容进一步拆给不同角色。

DNS 服务很容易被做成一个“能返回答案”的小程序。真正难的是承认它处在多个边界之间：隐私、性能、合规、协议正确性、用户规则、上游可信度和互联网治理历史。

一个好的解析器不应该只追求快。它还应该能解释自己的行为：为什么解析，为什么不解析，为什么拦截，为什么返回 451，为什么命中缓存，以及缓存命中后为什么仍然是一个正确的 DNS 响应。

这才是我们这次重构真正想解决的问题。
