DNS 看起來像網際網路裡最樸素的一環：給一個域名，拿一個地址。

很多人第一次理解 DNS，都會把它當成「網際網路電話簿」。這個比喻沒有錯，但只說了一半。電話簿至少還擺在你面前，而 DNS 查詢通常發生在你看不見的地方：打開網頁、啟動 App、同步郵件、存取 API、拉取系統更新，背後都可能先問一句：「這個名字對應哪台伺服器？」

如果這句話是明文傳輸，沿途網路設備可能看見它。如果解析器本身有策略，它也可能改變答案。如果快取做錯，解析器甚至可能為了效能返回一個協定上不夠正確的 DNS 報文。

dquery 仍處在小規模測試和持續完善階段，所以本文不會提供具體服務路徑、查詢入口或公開接入說明。這裡更想記錄的是一次自建遞歸解析器的工程經歷：我們怎樣拆分匿名查詢、個人配置、控制台和本地規則；怎樣處理 DoH 的快取陷阱；又怎樣在隱私、效能、合規和協定正確性之間做取捨。

## DNS 為什麼會變成信任問題

傳統 DNS 主要跑在 UDP/53 上。它簡單、快、相容性好，所以幾十年來一直是網際網路的基礎元件。但它誕生得很早，預設沒有加密，也沒有很好地防止路徑上的第三方觀察和篡改。

這意味著，在一些網路環境中，DNS 查詢可能被營運商、公共 Wi-Fi、閘道設備、中間盒或其他路徑觀察者看到。更糟糕的情況下，攻擊者還可能搶先返回偽造結果，讓使用者以為自己拿到了正常答案。

後來出現的 DoT、DoH、DoQ，本質上都是在修補這個歷史包袱：

- DoT 把 DNS 放進 TLS 連線，協定邊界清楚。
- DoH 把 DNS 放進 HTTPS，更容易接入瀏覽器和 CDN 生態。
- DoQ 把 DNS 放進 QUIC，希望在加密、低延遲、連線遷移和丟包恢復之間取得更好平衡。
- ODoH 進一步嘗試把「誰在問」和「問了什麼」拆開，讓代理知道使用者來源，但看不到查詢內容；目標解析器能解密查詢，但不直接看到使用者 IP。

不過，加密 DNS 很容易被誤解成「從此完全匿名」。這並不準確。DoH 主要保護的是用戶端到解析器之間這段鏈路。路上的人更難直接看到和修改 DNS 查詢，但解析器本身仍然會看到你問了哪個域名、問的是什麼記錄類型、請求大概來自哪裡、是否命中規則，以及最終選擇了哪個上游。

換句話說，DoH 不是讓 DNS 隱私問題消失，而是把信任對象從「沿途所有網路設備」縮小到「你選擇的解析器」。自建解析器的價值也正在這裡：至少日誌策略、上游選擇、快取行為、攔截規則和區域邊界可以由自己定義，並且能向使用者解釋。

## 先把幾個常見誤解拆開

討論 DNS 時，最容易把幾件事混在一起：根伺服器、國家頂級域名、遞歸解析器、營運商劫持、公共 DNS、加密 DNS。這些都和 DNS 有關，但它們不在同一層。

根伺服器負責告訴遞歸解析器：「`.com` 應該去問誰，`.cn` 應該去問誰，`.iq` 應該去問誰。」它不負責回答每一個具體網站的最終 IP。普通使用者日常存取網站時，更多接觸的是本機快取、路由器、營運商遞歸解析器、公共 DNS、DoH 解析器和權威 DNS。

所以，「根伺服器系統是否穩定」和「使用者日常拿到的 DNS 答案是否中立」，是兩個相關但不同的問題。

![DNS 分層與常見誤解：根區、國家頂級域、遞歸解析路徑和用戶設備不是同一層問題](https://files.js.gripe/files/fil_URqoWfEq4-y7JbJVYu95nxVC.png)

### 根伺服器問題要放回正確層級

早期中文網際網路裡，經常能看到一種說法：「中國沒有根伺服器，所以如果被美國制裁，域名系統可能一夜失效。」這類說法有歷史背景，但表述過於粗糙。

準確一點說，DNS 根伺服器系統有 13 個根伺服器標識，從 A-root 到 M-root，由多個獨立營運方管理。IANA 的根伺服器列表可以看到這些標識和營運方；Root Server Technical Operations Association 也說明，13 個根標識透過 anycast 分布到全球很多實例。

這裡至少要區分四層：

- 根伺服器標識營運權：誰負責營運 A-root 到 M-root 這些邏輯根標識之一。
- 根伺服器實例：某個根標識在全球不同地點部署的 anycast 節點。
- 國家頂級域名管理權：誰負責 `.cn`、`.iq`、`.ly` 這樣的 ccTLD 註冊局和權威 DNS。
- 遞歸解析路徑：普通使用者查詢域名時，實際用了哪個遞歸解析器，經過了哪些快取和網路路徑。

早期輿論常常把這幾層合在一起講，於是「沒有根標識營運權」被說成「沒有根伺服器」，「國家頂級域管理異常」被說成「根伺服器讓一個國家消失」，「營運商路徑污染」又被說成「根區被改寫」。這會讓討論變得很嚇人，但技術上並不準確。

伊拉克 `.iq` 和利比亞 `.ly` 更像是國家頂級域治理、權威 DNS、技術聯絡人和營運連續性問題。它們能提醒我們 ccTLD 治理很重要，但不應該被簡化成「根伺服器一鍵讓國家消失」。更完整的根區、ICANN、司法管轄和網路主權爭議，放到後面的「茶後閒談」裡再展開。

### DNS 答案不總是中立的

很多人以為 DNS 就像查字典：字典裡是什麼，答案就是什麼。但現實中的 DNS 解析鏈路很長，答案可能在不同層級被改變。

這種改變不一定都來自政治審查，也可能來自商業策略、安全產品、家長控制、企業內網策略、惡意劫持，或者單純的錯誤配置。

2003 年，VeriSign 推出過 Site Finder。使用者存取不存在的 `.com` 或 `.net` 域名時，正常 DNS 語義應該返回「這個名字不存在」。但 Site Finder 會把這些不存在的域名導向一個搜尋頁面。這個設計引發了很大爭議，因為許多程式並不只是在瀏覽器裡「打開網頁」：郵件系統、反垃圾規則、自動化腳本和網路設備也會依賴 NXDOMAIN 這個語義。

2014 年土耳其封鎖 Twitter 和 YouTube 時，也發生過公共 DNS 被攔截的案例。許多使用者把 DNS 改成 Google Public DNS，希望繞過本地解析限制；隨後 Google 表示當地網路中出現了偽裝成 Google DNS 的伺服器，用來阻斷相關服務。這說明公共 DNS 不是魔法開關。只要查詢仍然走明文或路徑可被接管，中間網路仍然可能攔截、冒充或阻斷它。

再看更大範圍的研究，GFWatch 對中國大陸 DNS 過濾做過長期測量。USENIX Security 2021 論文《How Great is the Great Firewall? Measuring China's DNS Censorship》介紹了一個大規模、長期的 DNS 過濾測量平台，並觀察到 DNS 過濾、偽造記錄注入，以及部分公共解析器快取受到污染的現象。

對 dquery 這類自建解析器來說，這些案例的啟發不是簡單得出某個政治結論，而是提醒我們：DNS 結果可能受到路徑、上游和快取的共同影響，解析器需要盡可能區分這些來源。

## 我們要做的不是黑盒解析器

一個公開 DNS 服務，如果只返回答案，卻不解釋答案從哪裡來，就很容易變成新的黑盒。

dquery 的目標不是做一個神祕的「萬能 DNS」，而是把解析過程拆成幾個可以理解的步驟：

![dquery 遞歸解析器處理流程：入口判斷、區域與帳戶策略、本地規則、正規化快取、上游遞歸和 DNS 回應](https://files.js.gripe/files/fil_lufD3AWsokIl2nU0HuOwaJsW.png)

```text
用戶端請求
  -> 入口判斷：匿名、個人或控制台
  -> 區域與帳戶策略
  -> 本地域名規則
  -> 正規化快取
  -> 上游遞歸解析
  -> DNS 回應
```

這樣做的好處是，每一次結果都盡量有來源：

- 如果域名被使用者規則阻斷，應該能說明這是本地規則命中。
- 如果域名返回 NXDOMAIN，應該區分它是上游真實返回，還是本地規則主動返回。
- 如果匿名入口因區域策略不可用，應該明確返回對應 HTTP 狀態，而不是偽裝成服務故障。
- 如果結果來自快取，也應該保證 DNS 報文仍然符合協定，而不是為了命中率犧牲正確性。

這聽起來像細節，但這些細節決定了解析器能不能被信任。

## 本地規則：不是所有域名都需要問上游

解析器不一定只是上游 DNS 的傳聲筒。在真正回源之前，dquery 會先檢查使用者 profile 和規則集。

如果某個域名命中本地策略，解析器可以選擇：

- 正常放行，繼續查詢上游。
- 返回 NXDOMAIN，表示這個名字不存在。
- 返回阻斷頁地址，讓使用者知道它被攔截。
- 返回策略錯誤，提示這是規則或區域限制導致的結果。

這類本地預處理有幾個實際意義。

第一，它可以減少不必要的上游查詢。廣告、追蹤、惡意域名如果已經被使用者明確加入阻斷規則，就沒有必要再把請求交給第三方遞歸解析器。

第二，它減少了被阻斷域名的外洩。被本地規則處理的域名，不會繼續暴露給上游 DNS 服務。

第三，它允許「千人千面」。不同個人配置可以綁定不同 profile：有人希望只攔截惡意域名，有人希望額外攔截廣告和追蹤，有人則希望盡量保持原始解析。公開解析器如果只有一份全局規則，很難兼顧這些需求。

但這裡也要保持克制。解析器不應該偷偷改答案，更不應該讓使用者誤以為所有結果都來自權威 DNS。只要發生本地處理，就應該在日誌、控制台或可觀測資訊中留下清楚說明。

## 區域策略：明確拒絕比假裝故障更好

公開 DNS 服務還會碰到合規和濫用問題。

某些地區對公共解析服務、加密 DNS 或繞過本地解析策略的入口有不同要求。如果一個匿名 DoH 入口被大規模濫用，風險最終會落到服務提供者身上。

因此，我們把幾類入口拆開：

- 前端查詢頁面：更像網頁工具，應該盡量穩定可用。
- 匿名解析入口：適合基礎公共查詢，但可以根據區域策略拒絕服務。
- 個人解析入口：和帳戶、profile、規則、配額綁定，更適合長期使用。
- 控制台入口：用於管理規則、查看狀態和配置個人解析器。

如果匿名入口在某些地區不可用，我們更傾向於返回 HTTP 451，而不是含糊地返回 403、502 或直接逾時。451 的含義是「因法律原因不可用」。它至少告訴使用者：服務不是壞了，也不是解析器崩了，而是這個入口在當前條件下不能交付。

這裡尤其包括中國大陸。原因不是技術上做不到，而是合規成本和治理風險都太高。公共遞歸解析器一旦面向中國大陸提供服務，就很容易被要求接入本地監管和內容治理鏈條：日誌留存、濫用處置、域名處置，甚至對特定域名返回策略性結果。對大型公共 DNS 服務商來說，這可能被包裝成「合規營運」；但對我們來說，這會讓解析器從「盡量解釋答案從哪裡來」，滑向「在源頭上配合改寫答案」。

這也是我們不希望 dquery 在當前階段向中國大陸開放解析器服務的原因。一個解析器如果為了進入某個市場而必須變成不中立的上游，那它就不再只是保護用戶端到解析器之間的鏈路，而是在遞歸解析源頭製造另一層污染。部分本地公共解析服務在特定域名上返回策略性答案，本質上也接近這個問題：加密傳輸保護了「到解析器為止」的路，卻不能保證解析器本身不參與改寫。

2010 年 I-root 中國節點事件也給了類似提醒。當時部分境外網路因為路由和任播路徑問題，拿到了異常 DNS 回答；後續公開報導提到，相關中國節點的路由通告被撤回以避免影響繼續擴散。這個案例並不是「根伺服器讓一個國家消失」，而是說明：本地 DNS 策略、任播節點和 BGP 路由一旦疊在一起，本來局部的污染或錯誤答案可能外溢到更大範圍。對自建遞歸解析器來說，最穩妥的邊界就是不要進入自己無法保持中立和可解釋性的合規環境。

這不是完美答案，但比沉默更誠實。

## 快取真正麻煩的地方：DNS ID

DNS 是高頻服務。沒有快取，源站壓力會很大，延遲也會升高。但 DNS 的快取又不能像普通網頁那樣粗暴處理，因為 DNS 報文本身有協定細節。

一個關鍵欄位是 Transaction ID，也就是 DNS 報文頭部最前面的 16 位 ID。RFC 1035 定義了 DNS 報文格式，其中頭部包含用於匹配查詢和回應的 ID 欄位。用戶端發起查詢時通常會生成一個 ID，回應必須把這個 ID 帶回來，用戶端才能確認「這個答案對應我剛才那次請求」。

DoH 的 GET 請求會把 DNS wire message 經過 Base64URL 編碼後放進 HTTP 請求中。RFC 8484 明確描述了這種形式。問題就來了：如果兩個用戶端查詢同一個域名、同一個記錄類型，但 DNS ID 不同，那麼編碼後的請求也不同。CDN 看到的是兩個不同 HTTP 物件，自然會把它們當成兩個不同快取物件。

協定文件其實已經注意到這個問題，並建議 DoH 用戶端在某些格式下使用 ID=0，以提高 HTTP 快取友好性。但現實中，我們不能假設所有用戶端都這麼做。

所以，服務端必須自己處理這個問題。

## 為什麼不把正規化全部放在邊緣腳本

最初我們考慮過把正規化放在邊緣腳本上：解析 DoH 請求裡的 DNS 報文，把 DNS ID 清零後構造快取鍵；命中快取時，再把回應裡的 ID 改回當前請求的 ID。

從協定上看，這個方案可行，快取命中率也好。但 DNS 查詢頻率很高，如果每個個人解析請求都經過邊緣腳本，請求數和成本很快會變成主要問題。

於是最終設計改成：正式 DoH 鏈路不依賴邊緣腳本做核心協定處理，正規化交給後端完成。

也就是說，後端會把 DNS ID 從快取鍵中剝離，但不會忽略其他真正影響答案的因素。一個安全的快取鍵，至少要考慮：

- 查詢域名。
- 記錄類型，例如 A、AAAA、HTTPS、TXT。
- 查詢類，通常是 IN。
- 影響結果的 DNS 標誌。
- 是否攜帶 ECS 等會改變答案的擴展資訊。
- 當前個人配置或 profile。
- 本地規則版本。
- 區域策略。
- 選擇的上游或線路。

這樣才能避免一個使用者的規則結果被另一個使用者誤用，也避免不同區域、不同策略、不同上游的結果混在一起。

命中快取後，後端再把回應報文前兩個位元組改回當前請求的 DNS ID。這樣用戶端看到的仍然是協定正確的回應。

這一步看似很小，但它是整個快取方案的核心：我們可以最佳化命中率，但不能破壞 DNS 的請求回應匹配機制。

## 反向代理和 CDN 應該做什麼

反向代理很適合做 TLS 終止、路由、限流和普通 HTTP 代理。但它不適合作為 DoH 二進位回應的核心改寫層。

原因很簡單：DoH 回應體是 DNS wire message，快取命中後仍然需要針對每個請求動態改寫前兩個位元組的 DNS ID。如果在反向代理的 body filter 裡硬做，會增加複製和 CPU 成本，也更容易在並發場景中引入難以排查的問題。

所以，我們把職責重新劃分：

```text
用戶端 DoH 請求
  -> CDN 或邊緣網路
  -> 反向代理路由
  -> 後端解析 DNS 報文
  -> 生成不含 Transaction ID、但包含真實語義維度的快取鍵
  -> 命中後改回當前請求的 response ID
  -> 返回協定正確的 DNS 回應
```

CDN 仍然有價值，但它不應該負責理解 DNS wire message。它更適合做第二層快取：只快取源站明確標記為可共享的回應。

因此我們讓源站透過 `Cache-Control` 表達快取意圖：

```text
源站 MISS 或 BYPASS:
Cache-Control: no-store

源站 HIT 或 STALE:
Cache-Control: public, max-age=..., s-maxage=...
```

這樣做的意思是：第一次沒有命中的請求，不讓 CDN 存；源站已經確認可以共享的命中結果，再允許 CDN 快取；CDN 只遵循 HTTP 快取語義，不參與 DNS 報文改寫。

## 個人解析入口的意義

匿名入口適合做基礎查詢，但不適合承載所有功能。個人解析入口的意義，不只是「換一個入口」，而是把解析行為和使用者 profile 綁定起來。

匿名入口可以保持最小能力：接受標準查詢，執行基礎限制，必要時按區域策略拒絕。

個人入口則可以支援更細的功能：

- 使用者自訂規則。
- 不同設備使用不同 profile。
- 家庭、行動端、伺服器分開策略。
- 查詢統計和異常觀察。
- 配額、限流和濫用控制。
- 將來接入帳戶系統或 SSO。

這比把所有人都放在同一個全局解析策略裡更清晰，也更容易解釋問題。

當某個域名解析異常時，我們可以判斷：是匿名入口限制、個人規則命中、上游異常、快取命中、區域策略，還是用戶端請求格式本身有問題。

目前這類個人入口和控制台能力仍然在逐步完善中，因此本文只討論設計邊界和工程取捨，不提供具體服務路徑或公開接入說明。

## DoH 能保護什麼，不能保護什麼

到這裡可以重新回答一個常見問題：用了 DoH，DNS 提供商還能看到主機名嗎？

答案是：能。

DoH 加密的是用戶端到 DoH 解析器之間的傳輸鏈路。它能防止很多路徑上的旁觀和篡改，但解析器必須解密請求，才能知道你要查什麼，也才能返回答案。

所以，DoH 的主要收益是：

- 公共 Wi-Fi 或中間網路更難直接看到 DNS 查詢內容。
- 路徑上的旁路搶答和普通 DNS 劫持更難成功。
- 瀏覽器、系統或應用可以用 HTTPS 基礎設施發起 DNS 查詢。
- 使用者可以選擇自己信任的解析器，而不是預設交給接入網路。

但 DoH 不能保證：

- 解析器營運者完全不知道你查了什麼。
- 上游返回結果一定中立。
- 所有網路審查或封鎖都失效。
- IP 層、SNI、流量特徵等其他資訊完全隱藏。
- 快取、日誌和帳戶系統沒有新的隱私風險。

這也是為什麼解析器要透明。與其宣傳「絕對隱私」，不如明確告訴使用者：我們保護哪一段，記錄什麼，不記錄什麼，哪些結果來自本地規則，哪些結果來自上游。

## 茶後閒談：根伺服器、ICANN 和「網路霸權」的說法

中文語境裡討論 DNS 時，偶爾會看到類似「控制根伺服器就控制網際網路命脈」「美國可以把某些網站從地球上抹除」的說法。2021 年圍繞 36 個伊朗相關網站被美國查封的討論，就常被放進這類敘事裡。

這類說法抓住了一個真實問題：如果域名註冊商、註冊局、託管服務、CDN 或支付合規服務處在某個國家的司法管轄內，當地法院命令和制裁規則確實可能影響這些域名或服務。但從 DNS 技術層面看，把它直接說成「美國透過根伺服器一鍵抹除網站」，就過度簡化了。

2021 年那次事件，更準確地說，是美國司法部門依據法院命令查封了一批具體域名。它影響的是這些域名的註冊和解析服務，而不是把伊朗國家頂級域 `.ir` 從根區刪除，也不是 ICANN 回收了某個國家頂級域。事實上，一些受影響媒體後來改用 `.ir` 域名繼續上線，這也說明事件主要發生在具體域名和司法管轄層面，而不是整個國家頂級域被根區移除。

這裡需要把幾層拆開：

```text
單個域名查封：
  例如某個 .com 域名被註冊商、註冊局或法院命令鎖定、改指向或接管。

TLD 委派變化：
  根區裡某個頂級域的 NS、DS、glue 等委派資料發生變化。

ccTLD 治理問題：
  某個國家頂級域的註冊局、權威 DNS、技術聯絡人或本地治理流程出問題。

根伺服器實例：
  全球各地部署的 anycast 節點，負責對外提供同一份根區資料。

遞歸解析路徑：
  普通使用者真正使用的營運商 DNS、公共 DNS、DoH 解析器和快取路徑。
```

如果只是查封一個具體域名，根區通常不需要變化，TLD 權威伺服器也仍然正常工作。使用者看到的是這個具體域名被跳轉到查封頁、無法解析，或被鎖定，但同一個 TLD 下的其他域名不受影響。

如果真的發生 TLD 層面的重新委派，那影響才會進入根區。比如某個 ccTLD 的管理者被更換，根區裡的 NS、DS、glue 等資料會更新。根伺服器實例隨後同步新的根區資料；遞歸解析器在快取過期後，會按照新的根區委派去找新的 TLD 權威伺服器。舊的 TLD 權威伺服器即使還在運行，也不再是公共 DNS 標準路徑的一部分。

如果某個 ccTLD 被退休並最終從根區移除，情況更明顯：公共根區不再告訴遞歸解析器「這個 TLD 應該去問誰」。舊權威伺服器在技術上仍然可以繼續回答直接查詢，但普通公共 DNS 鏈路不會自然走到那裡。除非某些網路使用替代根、私有根或固定舊資料，否則這個 TLD 就不再屬於全球公共 DNS 的一致命名空間。

所以，對 IANA/ICANN 的態度也不必走向兩個極端。一邊不能把它們描述成完全沒有歷史包袱的純技術烏托邦；另一邊也不應該把它們說成某個國家隨手關閉網際網路的按鈕。更準確的理解是：公共 DNS 根區是一套有歷史背景、有政治爭議、但也有公開流程、問責機制和社群參與結構的全球協調機制。

2016 年 IANA stewardship transition 完成後，美國政府與 ICANN 的 IANA 職能合約已經結束。今天的 ICANN 採用多利益相關方模式，政府、ccTLD 社群、技術社群、註冊商、註冊局、商業和非商業使用者、普通終端使用者都可以透過不同組織和委員會參與。它也有 Reconsideration、Independent Review Process、Ombudsman、Empowered Community 等問責機制。它們不能保證這套機制完美無缺，但至少說明公共根區治理不是一條單向命令鏈。

如果有人質疑「IANA/ICANN 的資料可信嗎」，最好的回應不是要求對方相信某個機構，而是把問題變成可驗證鏈條：根區登記可以查，根區檔案可以下載，根伺服器可以從不同網路測量，DNSSEC 可以驗證信任鏈，ccTLD 重新委派和退休流程有公開文件，第三方學術測量和營運商觀測也能交叉印證。

合理的「獨立自主」，應該更多放在韌性建設和治理參與上：建設本地遞歸解析能力、部署根伺服器實例、做好快取、啟用 DNSSEC 驗證、建立故障應急和測量系統、參與 ICANN、IETF、RIR、ccNSO、GAC 等國際機制。這些都能提高網路韌性。相反，如果另建一套與公共根區不相容的替代根，讓同一個域名在不同網路裡指向不同結果，反而會破壞全球網際網路最重要的特性：同一個名字在全球大體指向同一套公共命名空間。

所以，那類文章適合用來提醒我們：域名系統確實會受到法律、制裁、註冊商、註冊局和國際治理結構影響。但它不適合被直接解讀成「根伺服器一鍵關閉網際網路」。對一個 DoH 解析器來說，真正重要的不是複述陰謀論，也不是假裝 DNS 完全中立，而是盡量把答案來源講清楚：它來自根區委派、TLD 權威、上游遞歸、本地規則、快取命中、區域策略，還是某種查封、攔截或污染。

## 茶後坦言：DNS 查詢方式還會繼續變

DNS 查詢方式的演進，基本是一條從「預設信任網路」走向「盡量減少暴露面」的路。

UDP/53 足夠快，但它把查詢內容暴露給路徑。DoT 把 DNS 放進 TLS，協定邊界清楚。DoH 把 DNS 放進 HTTPS，部署和穿透能力更好，也更適合瀏覽器生態，但它會把信任集中到解析器。DoQ 試圖借助 QUIC 改善延遲和連線遷移。ODoH 則進一步把用戶端來源和查詢內容拆給不同角色，避免單一服務同時知道「誰在問」和「問了什麼」。

ODoH 當然不是免費午餐。它會帶來額外延遲、代理可用性、密鑰發布、部署複雜度，以及代理和目標解析器是否合謀的問題。它更適合作為長期演進方向，而不是一開始就強行加入核心鏈路。

對當前階段的 dquery 來說，更現實的目標是先把普通 DoH 做正確：入口清晰、規則透明、快取安全、區域策略明確、協定行為可靠。

## 最後的狀態

這次重構後，dquery 的邊界比以前清楚了很多：

- 匿名入口和個人入口分開。
- 本地規則可以在回源前處理域名。
- 區域策略用明確狀態表達，而不是偽裝成故障。
- 邊緣腳本不再承擔正式 DoH 鏈路中的高頻協定處理。
- 後端負責 DNS ID 正規化快取，並在命中時改回當前請求 ID。
- 快取鍵不只排除 DNS ID，還要保留真正影響答案的語義維度。
- CDN 只快取源站明確標記為可共享的結果。
- 未來可以考慮 ODoH，把使用者來源和查詢內容進一步拆給不同角色。

DNS 服務很容易被做成一個「能返回答案」的小程式。真正難的是承認它處在多個邊界之間：隱私、效能、合規、協定正確性、使用者規則、上游可信度和網際網路治理歷史。

一個好的解析器不應該只追求快。它還應該能解釋自己的行為：為什麼解析，為什麼不解析，為什麼攔截，為什麼返回 451，為什麼命中快取，以及快取命中後為什麼仍然是一個正確的 DNS 回應。

這才是我們這次重構真正想解決的問題。
