大模型刚开始进入软件时，最常见的形态是在界面旁边增加一个聊天窗口。

用户可以询问某个命令在哪里、一个错误是什么意思，或者让模型根据帮助文档给出操作步骤。这确实降低了软件的使用门槛，但模型与软件之间仍然隔着一层界面：模型能够回答问题，却不一定知道当前项目里真正存在什么，更不能稳定地操作软件内部的对象。

随后出现了另一条路线：让模型读取屏幕截图，模拟鼠标和键盘，像人一样寻找菜单、填写参数和点击按钮。

Computer Use 扩大了模型能够操作的软件范围，却没有从根本上解决专业软件中的语义问题。对于 CAD、CAE、EDA 和科学计算软件而言，模型不仅要知道按钮在哪里，还要知道：

* 当前选中的是哪个零件、面、特征或元器件；
* 一条线路在电气意义上连接到了哪个网络；
* 参数使用毫米、英寸、欧姆还是兆帕；
* 修改尺寸后哪些下游特征会失效；
* 仿真是否真正收敛；
* 结果对应的是哪组材料、载荷和边界条件。

当模型开始从“回答软件问题”转向“参与实际工作”，软件也就需要一种新的接口：它既不能只面向程序员，也不能只面向图形界面，而要让模型能够发现、理解和调用软件能力。

Model Context Protocol，也就是 MCP，正是在这样的需求下发展起来。

## MCP最初要解决的不是点击软件，而是连接碎片化

2024年11月25日，Anthropic 正式开源 MCP。

当时大模型已经可以生成代码、分析文档和调用函数，但一旦需要访问企业文件、数据库、代码仓库或业务系统，开发者仍然要为每一个数据源单独编写连接器。一个模型应用接入 Google Drive、Slack、GitHub、PostgreSQL 和本地文件系统，往往意味着五套互不兼容的集成。

Anthropic 将这一问题概括为模型被隔离在信息孤岛之外：模型能力不断提高，但真实数据和软件能力仍散落在不同系统中。MCP 因此被设计成一套开放标准，让数据源和工具只需提供一次标准化服务，就能被多个兼容的模型应用连接。最早公开的参考服务器便覆盖了 Google Drive、Slack、GitHub、Git、PostgreSQL 和 Puppeteer。MCP 的最初两位主要创建者是 David Soria Parra 和 Justin Spahr-Summers。

MCP 的结构受到 Language Server Protocol，也就是 LSP 的启发。

LSP 解决的是编辑器与编程语言工具之间的重复适配问题。过去，每种编辑器都要分别实现 Python、Java、C++ 等语言的补全、诊断和定义跳转；有了 LSP，语言服务器可以同时服务多种编辑器。

MCP 采用了类似思路：

> 不再让每一种模型应用分别适配每一套软件和数据源，而是由软件提供标准服务器，再由兼容的模型客户端连接。

MCP 使用 Host、Client 和 Server 架构，通过 JSON-RPC 交换消息。服务器可以公开三类核心能力：

* **Resources**：文件、数据库记录、工程对象、日志和其他上下文；
* **Tools**：查询、修改、执行、计算和导出等操作；
* **Prompts**：经过整理的任务模板和工作流程。

Host 是承载模型和用户交互的应用，Client 负责与某个 MCP Server 建立连接，Server 则把具体系统的数据和操作能力提供出来。

MCP 因此并不是新的求解器、建模内核或自动化引擎。它更像是模型与既有软件能力之间的一层通用接口。

## 从本地连接器到生产协议

MCP 在2024年公开时，首先适合本地文件、开发环境和桌面工具。它真正引起大型软件厂商重视，则与2025年的快速演进有关。

### 2025年3月：远程连接和权限控制开始成形

2025年3月的规范加入了基于 OAuth 2.1 的授权框架，以 Streamable HTTP 取代早期的 HTTP+SSE 传输方案，并增加工具注释，让客户端知道一个工具是否只读、是否具有破坏性。

这一步非常关键。

如果 MCP 只能连接用户电脑上的本地进程，它更像开发者实验工具；当它拥有远程传输、身份验证和权限描述后，企业软件才有条件通过云端服务提供 MCP。

### 2025年6月：工具返回结果变得更适合专业任务

2025年6月的版本增加了结构化工具输出、Resource Link 和 Elicitation。

结构化输出允许工具返回具有明确字段的数据，而不是一段模糊文字。对于工程软件，求解工具可以返回：

```text
求解状态
最大应力
最大位移
危险位置对象ID
单位
警告数量
结果文件
```

Elicitation 则允许服务器在执行过程中向用户请求必要信息，例如要求确认材料、单位、文件位置或操作范围。协议同时加强了 OAuth 资源服务器定位和令牌使用安全。

### 2025年：大型模型与平台厂商相继采用

MCP 最初由 Anthropic 提出，但很快不再局限于 Claude 生态。

Microsoft 在2025年3月为 Copilot Studio 推出 MCP 预览，并于5月宣布正式可用。连接 MCP Server 后，服务器发布的工具和数据可以自动加入智能体；当服务器更新工具时，Copilot Studio 也可以动态同步，而不必手工重新建立每一个 Action。Microsoft 还把 MCP 接入现有连接器体系，以继续使用虚拟网络、数据防泄漏和多种身份验证机制。

OpenAI 随后在 API、ChatGPT Apps 和智能体工具体系中采用 MCP。开发者可以让模型连接远程 MCP Server，限制允许调用的工具，并为写入操作设置审批要求；ChatGPT 的自定义应用同样以 MCP 作为连接工具和内部数据的重要基础。

GitHub 发布并维护官方 GitHub MCP Server，让不同 IDE 和智能体读取仓库、Issue 和 Pull Request，创建任务，并调用代码安全等功能。组织还可以使用 MCP 策略和注册表限制允许运行的服务器。

Google Cloud 在2025年为数据库工具箱加入 MCP，并在同年12月宣布为 Google 服务提供官方 MCP 支持。Google 对此给出的原因也很直接：依赖社区服务器要求开发者分别安装和维护多个本地实现，容易形成脆弱的集成，因此需要由服务提供方维护远程、可治理的官方端点。

MCP 至此完成了一次重要转变：

> 它从 Anthropic 提供的开放连接方案，逐渐变成不同模型、智能体平台和软件厂商共同采用的接口层。

### 2025年末：进入中立治理

2025年11月的规范继续增加 OpenID Connect 发现、增量授权、工具显示信息和实验性的 Tasks。Tasks 用于跟踪耗时较长、需要轮询状态或延迟获取结果的任务，对编译、批量处理和工程仿真尤其重要。该版本还正式建立了治理结构、工作组和 SDK 分级制度。

2025年12月，Anthropic 将 MCP 捐赠给 Linux Foundation 下成立的 Agentic AI Foundation。AAIF 的创始项目还包括 Block 的 goose 和 OpenAI 的 AGENTS.md，成员包括 Anthropic、OpenAI、Microsoft、Google、AWS、Cloudflare 和 Bloomberg 等机构。

这一变化减少了软件厂商对“接入竞争对手私有协议”的顾虑。MCP 的治理不再只由某一家模型公司控制，而是逐渐成为中立的开源基础设施。

截至2026年7月，稳定规范仍为2025-11-25。计划于2026年7月28日发布的下一版正在进一步弱化协议级会话，转向更适合普通 HTTP 基础设施的无状态核心，并通过扩展机制承载 Tasks、交互式界面等能力。

## 为什么软件厂商开始把产品做得对模型友好

软件厂商支持 MCP，并不只是为了追随一个热门协议。

真正的变化是：**模型正在成为新的软件入口。**

过去，用户先打开 CAD、EDA 或办公软件，再从菜单中选择功能。未来，用户可能先向 Codex、Claude、Copilot、ChatGPT 或企业内部智能体提出目标：

> 检查这套电路的供电问题。

> 修改模型后重新比较应力结果。

> 找出装配体中的干涉并生成报告。

> 读取项目状态，创建修复任务并提交代码。

智能体再决定需要调用哪些软件。

当这种工作方式逐渐普及时，软件能否被模型正确发现、理解和调用，就会像文件格式、插件生态和云端 API 一样，成为产品竞争力的一部分。

### 保住专业软件在工作流中的位置

模型能够生成代码，也可以调用开源库重新实现部分功能。如果传统软件始终只能由人通过界面操作，智能体便可能绕开它：

* 直接生成通用几何文件；
* 调用其他仿真服务；
* 使用开源库处理数据；
* 依赖第三方脚本完成转换；
* 转向接口更开放的竞争产品。

厂商提供 MCP，可以让自己的几何内核、求解器、元件模型、设计规则和项目数据继续成为智能体工作流中的权威执行环境。

Autodesk 对 MCP 的定义便强调，服务器负责验证请求、执行权限、访问数据并返回结果，而不是让模型直接绕过产品内部控制。

### 避免为每一种模型重复开发插件

假设一家软件厂商要同时支持 ChatGPT、Claude、GitHub Copilot、Gemini、Cursor 和 Codex。

没有统一协议时，厂商可能需要分别适配六套工具格式、身份验证、配置方法和生命周期。模型平台每次更新，连接器也可能需要跟着修改。

有了 MCP，软件厂商可以维护一套服务器，再由多个兼容客户端发现其中的工具。Autodesk Fusion 和 MathWorks 的官方实现已经同时列出 Claude、VS Code、GitHub Copilot、Codex、Gemini CLI 等不同客户端。

这不是完全消除适配工作，而是把原来的多对多连接：

```text
多个模型 × 多种软件
```

转化为：

```text
模型客户端 ↔ MCP标准 ↔ 软件服务器
```

### 把已有API开放给更多普通用户

SOLIDWORKS、NX、MATLAB、AutoCAD 和 Ansys 很早就拥有宏、脚本、插件或编程接口。

但这些接口主要面向开发者。普通工程师即使知道软件能够自动化，也未必会编写 C# COM 程序、NX Open 插件、MATLAB 工具箱或 AutoLISP 脚本。

MCP 可以把底层接口包装成模型能够理解的语义工具：

```text
读取装配结构
查找欠定义草图
修改材料
检查悬空输入
生成网格
运行测试
读取求解日志
导出STEP文件
```

用户只需要说明目标，模型负责选择工具和组织步骤，软件原有 API 则继续负责确定地执行操作。

### 降低软件学习和支持成本

专业工程软件通常拥有大量命令、模块和参数。新用户可能花很长时间寻找一个功能，熟练用户在面对不常使用的模块时也需要重新查阅文档。

Siemens 在 Designcenter X NX 中加入 Copilot，让它结合近期命令和当前任务提供操作指导，减少复杂流程的重新学习时间。

Proteus ProPilot 则能够读取当前原理图、程序代码和仿真数据，结合实际 MCU 接线提供外围设备代码、元件建议、故障分析和软件操作指导。

即使这些能力并不全部通过公开 MCP 服务器呈现，它们体现了同一个方向：软件帮助系统正在从通用文档搜索，转向理解用户当前项目。

### 允许个人和企业选择模型

软件厂商不可能保证某一种模型永远在能力、成本、延迟、隐私和地区可用性上适合全部用户。

MCP 将软件能力与模型选择适当分开。个人可以使用自己已经订阅的模型，企业可以接入获准的云模型、私有模型或本地模型，软件厂商则继续控制工程对象和操作权限。

Proteus 允许用户选择 GPT、Claude、DeepSeek 和自托管模型；MathWorks 的 MCP 与 Agentic Toolkit 也支持多种编码智能体。

### 防止第三方替厂商定义接口

当厂商没有提供 MCP 时，社区通常会利用已有 API 先做出一个版本。

第三方实现可以快速验证市场需求，却也可能出现：

* 工具命名和参数不统一；
* 不同软件版本兼容性不足；
* 依赖任意脚本执行；
* 无法使用软件内部身份和权限；
* 操作失败后缺少事务与回滚；
* 项目停止维护。

如果第三方项目首先获得大量用户，它就可能成为模型理解该软件能力的事实标准。厂商后来即使推出官方方案，也要面对既有兼容习惯。

因此，厂商提供官方 MCP 不只是增加功能，也是重新掌握对象语义、权限边界和版本兼容的定义权。

## “支持MCP”其实有四种不同状态

讨论软件是否支持 MCP 时，不能简单地只写“有”或“没有”。

### 第一类：厂商提供正式MCP Server

服务器由软件厂商维护，直接访问产品内部对象或云服务。

这类方案通常最容易获得：

* 准确的对象语义；
* 软件版本适配；
* 官方身份验证；
* 企业权限；
* 错误状态；
* 正式支持。

### 第二类：产品内置AI，并通过内部MCP或类似接口工作

用户能够在软件内使用上下文感知的 AI，模型也可能通过本地接口访问软件，但厂商未必把完整服务器作为独立开发产品公开。

Proteus 9.1 的实际使用便属于这一方向。在本文作者使用的环境中，Codex 可以通过本地8001端口连接 Proteus，读取工程上下文并调用相应能力。对普通用户而言，它和 ProPilot 的产品内体验共同构成了模型与原理图、代码和仿真的连接。

### 第三类：厂商尚未提供专用MCP，但已有成熟API

第三方、合作伙伴或企业内部团队可以基于官方 API 开发 MCP。

SOLIDWORKS 的 COM API 和 Siemens NX Open 都属于这一基础。MCP 并不会取代这些接口，而是将它们组织成更适合模型调用的工具。

### 第四类：主要依靠界面自动化

软件缺少稳定 API，只能使用截图、鼠标、键盘、窗口控件或文件导入导出。

这种方式仍然可以接在 MCP 工具后面，但它本质上仍是 RPA 或 Computer Use，稳定性和语义精度都低于直接访问软件对象。

### GitHub：从代码上下文到软件开发动作

GitHub 官方 MCP Server 可以在 VS Code、Visual Studio、JetBrains、Xcode 和其他兼容客户端中使用。它不仅能读取仓库信息，还可以创建 Issue、列出 Pull Request、启动部分 Copilot 云任务，并调用代码扫描或密钥检测功能。具体工具继续继承 GitHub 原有权限和订阅要求。

它展示的是现代平台软件的典型路线：把原来分布在网页、API 和 Copilot 中的能力，整理成一个可以被多种智能体调用的正式入口。

### Autodesk Fusion：传统CAD厂商的完整参考方案

Autodesk Fusion 提供两个定位不同的 MCP Server。

本地 Fusion MCP 连接正在运行的桌面软件，可以检查活动文档、执行命令并实时建模。Fusion Data MCP 运行在 Autodesk 云端，用于查询和管理 Hub、项目、文件夹、条目和权限。

这种拆分很有代表性：

```text
本地MCP：操作当前设计
云端MCP：管理项目和协作数据
```

它说明传统桌面软件不必全部迁移到浏览器，仍然可以通过本地 MCP 把正在运行的专业应用连接给外部模型。

### Ansys：在成熟Python生态上增加模型接口

Ansys 并没有重新为大模型开发一套仿真系统，而是在 PyAnsys 基础上增加 MCP。

当前 PyAnsys 文档已经列出面向 Mechanical、Fluent、MAPDL、AEDT 和 Lumerical 的 MCP 项目，同时提供 PyAnsys Common MCP，帮助不同产品建立统一服务器。

模型因此可以围绕现有 PyAnsys 能力组织工作：

```text
读取分析设置
检查材料和边界条件
修改模型对象
生成网格
启动求解
读取日志
提取结果
```

MCP 负责工具发现和调用，实际仿真仍由 Ansys 产品与 PyAnsys 完成。

### MATLAB和Simulink：不只提供工具，还提供专业方法

MathWorks 的 MATLAB MCP Core Server 可以启动或连接现有 MATLAB 会话，检测工具箱、静态检查代码、执行代码、运行脚本和测试。服务器还支持通过扩展文件增加企业或用户自己的工具。

Simulink Agentic Toolkit 则进一步结合了 MCP Tools 与 Agent Skills。

工具负责读取、编辑、查询和测试 Simulink 模型；Skills 则提供模型化设计、测试和工程实践知识。现有工具可以读取系统层级、信号流和参数，增加模块与线路，并通过 Gherkin 测试验证需求。

这体现了一种新的软件设计思路：

> 只给模型操作权限还不够，还要告诉模型在这个专业领域中应当怎样正确使用这些权限。

### Proteus：让模型同时看到电路、代码和仿真

Proteus 的价值不只在于能够绘制原理图，而在于它把微控制器程序与电路仿真放在同一个环境中。

在本文作者实际使用的 Proteus 9.1 中，Codex 可以通过本地8001端口接入 MCP，与当前工程进行交互。

Proteus ProPilot 的公开能力则包括实时分析原理图、读取代码和仿真数据、根据 MCU 引脚连接生成 SPI、I²C、PWM 等代码、修改元件数值、导航对象并协助定位电路或固件问题。它还允许用户选择多种云端或自托管模型。

这使模型不必只根据截图猜测某根线接在哪里，而可以同时结合：

```text
原理图连接
元件参数
MCU引脚
嵌入式代码
编译信息
仿真数据
```

Proteus 是 MCP 和上下文感知 AI 进入传统 EDA 软件的一个实际案例，但它并不是唯一方向。相同思路也正在 CAD、CAE 和科学计算软件中出现。

### Siemens NX：已经重视AI入口，直接建模MCP仍有发展空间

Siemens 已经上线官方 MCP Server，为智能体提供西门子产品、开发文档、API 和技术资源搜索。这个服务器目前主要服务信息和开发者内容，而不是直接操作 NX 几何模型。

Designcenter X NX 则已经加入内置 Copilot。它结合当前任务和近期命令，为用户提供工程工作流指导、命令建议和错误处理信息。

对于更深层的建模控制，NX Open 仍然是重要基础。企业可以将经过批准的 NX Open 能力封装成内部 MCP，例如：

```text
读取零件和特征树
查询表达式
修改参数
检查失效引用
执行干涉分析
导出指定格式
```

因此，Siemens 的现状不是“不重视 MCP”，而是已经在开发者和知识入口采用 MCP，同时让 NX 的模型操作继续依赖其成熟的产品 API 和内置 Copilot。

### SOLIDWORKS：第三方利用成熟COM接口先行

SOLIDWORKS 官方 API 是拥有数百项函数的 COM 编程接口，可以通过 VBA、VB.NET、C# 和 C++ 直接访问设计功能。

目前公开的 SOLIDWORKS MCP 主要由社区开发。

一类服务器只提供 SOLIDWORKS API 文档检索，帮助模型寻找接口、枚举和示例；另一类服务器通过 COM 和 VBA 直接操作软件，覆盖草图、建模、装配、工程图、分析和导出。部分项目已经提供大量工具，但开发者仍将其标记为研究、业余或 Alpha 状态。

这说明“第三方已经实现”与“已经适合生产”不是同一个结论。个人可以用它探索，企业则需要重新检查工具范围、异常处理、版本锁定和权限。

### AutoCAD和Blender：社区证明了接口需求

AutoCAD 的第三方 MCP 可以通过 AutoLISP、文件通信和 ezdxf 操作图层、图元、块、文字、标注、视图和P&ID符号，也可以在没有 AutoCAD 的环境中直接生成 DXF。

Blender 社区 MCP 能够读取场景、创建对象、设置材质、渲染、导出并执行 Python。其常见架构是在 Blender 内安装插件，再通过本地 Socket 与 MCP Server 通信。

这些项目证明，拥有成熟插件和脚本接口的软件很容易被社区 MCP 化。

但任意 Python、AutoLISP 或宏执行也会扩大风险。模型一旦能够执行未经限制的代码，权限范围可能从“修改当前模型”扩大到读取文件、启动进程甚至访问网络。因此，正式产品更适合提供范围明确的语义工具，而不是只开放一个万能的 `execute_code`。

## 官方MCP与第三方MCP各自实现了什么

官方和第三方不是简单的好坏关系。

| 维度   | 官方MCP           | 第三方MCP            |
| ---- | --------------- | ----------------- |
| 对象语义 | 可直接使用软件内部对象和状态  | 依赖公开API、宏、脚本或文件解析 |
| 版本兼容 | 可以随产品版本共同维护     | 软件升级后可能出现失效       |
| 身份权限 | 可以接入厂商账户与企业策略   | 常继承本地进程或API密钥权限   |
| 功能范围 | 通常较克制，只开放受支持能力  | 往往更积极覆盖实验性功能      |
| 迭代速度 | 受正式发布周期影响       | 社区开发通常更快          |
| 技术支持 | 有厂商文档和支持渠道      | 依赖维护者与社区          |
| 风险   | 可能受许可、订阅和平台策略限制 | 可能包含任意代码执行或供应链风险  |

官方 MCP 更适合处理身份、项目权限、云端数据和稳定对象。

第三方 MCP 则更容易填补厂商尚未覆盖的场景，或者针对某一家企业的具体流程进行定制。

两者未来很可能长期并存：官方提供稳定核心，社区和企业在其上增加专业工作流。

## MCP与类似技术分别解决什么问题

MCP 并不是软件智能化所需的唯一技术。

### 软件API和SDK

API 是执行层。

SOLIDWORKS COM、NX Open、PyAnsys、MATLAB Engine 和 Blender Python API 真正负责读取对象、修改项目和运行计算。MCP 通常建立在它们之上，而不是替代它们。

### Function Calling

Function Calling 让模型在一次应用请求中选择开发者预先声明的函数。

它适合一个应用内部的工具调用；MCP 则进一步规定了独立客户端和服务器怎样连接、发现工具、取得资源和协商能力。同一个 MCP Server 可以被多个兼容应用使用。

### OpenAPI

OpenAPI 描述 HTTP 服务的路径、参数、请求体、返回结构和认证方法。

它面向一般程序调用；MCP 则面向模型和智能体，增加了工具发现、Resources、Prompts、生命周期和模型交互语义。已有 OpenAPI 服务可以被封装或转换成 MCP，但本地桌面软件的对象模型仍需要专门适配。

### A2A

A2A 主要解决智能体之间的发现、委派和任务交接。

MCP 解决智能体如何连接工具，A2A 解决多个智能体如何协作。例如设计智能体可以把验证任务交给仿真智能体，仿真智能体再通过 MCP 调用 Ansys。

### RPA和Computer Use

RPA 与 Computer Use 操作图形界面。

它们适合没有 API 的遗留软件、视觉检查和少量边缘步骤，但容易受到窗口布局、语言、分辨率、弹窗和软件版本变化影响。

更合理的优先顺序是：

```text
软件API或SDK
      ↓
官方或第三方MCP
      ↓
受控脚本与命令接口
      ↓
RPA或Computer Use
```

## 对个人用户意味着什么

对个人用户而言，MCP 最直接的价值不是“一句话自动完成所有设计”，而是减少重复说明。

过去遇到电路或模型问题，用户需要：

* 截取界面；
* 标出元件；
* 描述连接；
* 复制代码；
* 解释参数；
* 上传日志。

模型仍可能因为看错一个引脚或单位而从一开始就判断错误。

通过 MCP，模型可以先读取当前工程，再回答：

> 哪些器件没有接入电源网络？

> 哪个草图没有完全定义？

> 这组边界条件是否缺少约束？

> 当前代码与实际 MCU 引脚是否一致？

> 修改前后的应力和网格质量有什么变化？

它也可以帮助新用户快速了解陌生项目，解释对象关系，并给出下一步建议。

但软件能够被模型操作，并不代表设计结果自动可信。代码编译成功不等于硬件安全，仿真完成不等于工况合理，模型重建成功也不等于零件能够制造。

更稳妥的个人工作流是：

```text
读取项目
→ 解释当前状态
→ 提出修改方案
→ 用户确认
→ 执行有限修改
→ 重新编译、重建或求解
→ 检查结果与日志
```

## 对企业意味着什么

企业使用 MCP，真正需要关注的不是模型节省了多少次鼠标点击，而是设计能力能否被标准化、授权和审计。

企业可以把自己的规范整理成工具：

```text
检查电源与接地
检查悬空输入
检查未定义草图
检查装配干涉
检查材料和单位
执行标准仿真
生成设计审查报告
```

不同项目可以复用同一套检查流程，新成员也能更快理解历史工程。

与此同时，企业必须对 MCP Server 进行治理：

* 只允许批准的服务器；
* 区分只读、建议、修改和高风险操作；
* 为工具设置白名单；
* 保留修改前后的对象差异；
* 记录使用的模型、工具和参数；
* 对外发数据、删除和覆盖操作要求确认；
* 为重要工程建立检查点和回滚；
* 把编译器、规则检查器和求解器结果作为证据。

GitHub、Microsoft 和 OpenAI 都已经把服务器审批、组织策略、工具权限和写入确认纳入企业 MCP 使用方式，这说明 MCP 进入生产环境后的核心问题已经从“能不能连接”转向“谁可以连接、允许做什么、怎样留下记录”。

## 对软件设计方意味着什么

软件过去主要服务两类接口：

```text
面向人的图形界面
面向程序员的API
```

模型进入工作流后，软件还需要第三类接口：

```text
面向智能体的语义工具
```

面向模型的工具不应该只是：

```text
点击第17个按钮
打开第5个窗口
选择下拉框第3项
```

而应直接表达任务意图：

```text
读取器件连接
检查欠定义草图
修改指定材料
执行干涉分析
生成网格
读取求解日志
导出模型
```

一个成熟的工程 MCP 还应具备：

* 稳定的对象标识；
* 明确的单位和坐标系；
* 输入范围和类型检查；
* 修改前差异预览；
* 事务与撤销；
* 运行进度和取消；
* 结构化错误信息；
* 软件与工具版本；
* 可核验的执行结果。

软件设计方也不应只把现有数百个底层 API 原样暴露给模型。工具过多、名称相近或参数复杂，都会增加模型选错工具的概率。

更合理的方式是把底层接口重新组合成少量语义清晰的任务工具，并提供专业 Skills、规则和示例，让模型不仅“有能力调用”，还知道“应当怎样调用”。

## 结语：软件正在增加第二类使用者

传统软件并不会因为 MCP 出现，就放弃图形界面、插件和脚本。

人仍然需要直接观察模型、修改细节、比较方案并承担最终责任。软件 API 仍然负责确定地执行专业操作，Computer Use 也仍然可以补足没有开放接口的界面步骤。

真正发生变化的是：软件正在增加一类新的使用者——代表人员提出查询和操作请求的模型。

这要求软件不再只考虑“人能不能看懂界面”，还要考虑：

* 模型能否准确识别项目对象；
* 能否知道一个操作的影响范围；
* 能否在受限权限下完成任务；
* 能否根据结构化结果自行纠错；
* 人员能否看见、拒绝和追溯它的行为。

MCP 从2024年的开放连接实验，经过远程传输、授权、结构化输出和中立治理，逐渐成为模型连接软件的一种公共基础设施。

现代云平台率先采用它，是因为这些产品原本就拥有成熟 API 和远程身份体系；传统工程软件开始重视它，则是因为模型正在进入设计、仿真、编程和项目管理的核心流程。

未来软件之间的竞争，可能不只比较谁的功能更多、求解更快或界面更好，还会增加一个新的问题：

> 当用户通过模型发起任务时，这款软件是否能够被准确理解、安全调用，并返回可以核验的专业结果？

MCP 不会替代工程师，也不会自动让模型懂得所有设计原则。

它真正改变的，是人与专业软件之间不再只有鼠标、键盘和固定 API。模型开始成为新的交互层，而软件也必须学会用一种既对模型友好、又仍然由人员控制的方式开放自己。
